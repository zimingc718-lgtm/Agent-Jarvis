# Agent-Jarvis AI 规范控制

## 1. 目的与适用范围

本文件只定义项目治理规范，不定义产品功能。产品功能、范围、架构、模块、测试和发布目标必须在用户确认后，才能写入 `project/` 下的受控说明书。

规范采用“必须、应当、可以”三个等级。“必须”是受控流程的强制要求；无法自动判断的事项必须由证据文件、评审记录或测试结果支撑。

## 2. 不可绕过的基本原则

1. **需求入口原则**：用户原始需求必须先保存，再派生产品需求说明书。
2. **确认前不发散原则**：用户未确认产品定义前，不得创建具体功能需求、架构设计、模块任务、测试矩阵或发布结论。
3. **需求基线原则**：产品需求说明书必须由用户确认，且每条需求必须有唯一 ID、优先级和验收标准。
4. **严格派生原则**：架构、模块、任务和测试必须从已确认需求派生，不得静默增加或删除需求。
5. **测试前置原则**：测试及通过标准必须在编码前定义。
6. **证据完成原则**：任务只有在依赖完成且必选验证实际通过后才能标记 DONE。
7. **一致性原则**：批准后的需求、架构、模块、测试和发布说明书应形成基线；基线变化必须走变更流程。
8. **变更闭环原则**：任何实质变更必须记录影响范围、评审结论、验证证据和关闭状态。
9. **自下而上证据原则**：正式反馈必须先有测试、运行、用户反馈或其他可定位证据，再形成观察、归因和建议。
10. **真实入口原则**：涉及用户交互、接口、CLI 或服务的验收，必须通过真实入口验证。
11. **发布门禁原则**：所有 MUST 需求必须有当前通过证据；开放的重要反馈或阻塞变更会阻止发布。
12. **真实入口对应原则**：测试矩阵每一行的命令必须执行该覆盖需求点对应的真实入口（HTTP 路由、渲染组件、CLI），不得以相邻单元测试或纯函数断言充当该需求点的唯一证据。
13. **契约无悬空原则**：新增 API 字段或端点，必须在同一变更内提供并验证真实消费者；新增前端能力，必须有真实入口可观察断言。任一端单独通过不构成需求完成证据。
14. **安全配置显式失败原则**：加密密钥、鉴权密钥等安全相关配置缺失时必须 fail-fast，禁止静默降级默认值；相关错误路径必须映射到用户可读状态。
15. **验收标准逐条断言原则**：需求验收标准中每个可观察动作必须各自对应至少一条测试断言，G2/G3 评审记录须逐条列明。
16. **无残留旧代码原则**：修改或重新定义一段代码/样式/规则时，被取代的旧实现必须在同一变更内删除，不得新旧并存。被评审判定为「暂缓（DEFERRED）」而刻意保留的代码除外，且必须在架构说明书或 CR 中显式记录保留理由。可执行强制：`tsconfig.json` 开启 `noUnusedLocals` / `noUnusedParameters`，`npm run test:typecheck` 对未使用的局部/导入/参数报错。

## 3. 标准说明书与责任边界

| 说明书 | 路径 | 责任人 | 内容 |
|---|---|---|---|
| 需求输入 | `project/00_input/需求输入.md` | 产品 owner | 原始需求、来源、时间、状态 |
| 产品需求说明书 | `project/01_specification/产品需求说明书.md` | 产品 owner | 目标、范围、非目标、需求、验收标准、风险 |
| 架构设计说明书 | `project/02_solution/架构设计说明书.md` | 架构角色 | 架构、数据流、模块边界、接口、技术选型、风险 |
| 模块任务开发说明书 | `project/03_modules/模块任务开发说明书.md` | 模块开发角色 | 模块职责、任务拆解、依赖、状态、代码入口 |
| 测试说明书 | `project/04_tests/测试说明书.md` | 测试角色 | 测试矩阵、命令、通过标准、覆盖追踪 |
| 证据记录 | `project/05_evidence/` | 测试/质量角色 | 测试、运行、审核和用户反馈证据 |
| 变更记录 | `project/06_changes/` | 变更提出人与评审角色 | 变更原因、影响范围、评审、验证、关闭 |
| 版本发布控制说明书 | `project/07_releases/版本发布控制说明书.md` | 发布 owner | 版本号、发布条件、证据清单、回滚方式 |

## 4. 角色责任

- 产品 owner：确认需求正确性、范围、优先级和验收标准。
- 架构角色：确认技术结构、边界、接口和可行性。
- 模块开发角色：确认任务拆解、实现路径和代码变更。
- 测试角色：确认测试充分性、执行证据和失败回流。
- 发布 owner：确认版本范围、发布证据和回滚方案。

一人可以承担多个角色，但受控评审记录必须标明当前角色和检查结论。

## 5. 完成定义

任务完成必须同时满足：需求已确认、任务已实现、依赖已完成、必选测试当前 PASS、证据已保存。

项目可发布必须同时满足：需求、架构、模块、测试和发布说明书一致；所有 MUST 需求通过当前验证；开放阻塞项关闭；发布清单生成。

## 6. UI 开发规范控制

UI 开发规范属于项目治理基线，不属于业务功能定义。任何 UI 功能、页面、交互、文案和验收标准，必须先从已确认产品需求派生，不得在 UI 设计或实现阶段发散。

UI 工作必须执行 docs/UI_STANDARD.md。最低控制项包括：Design Tokens、Component-Driven Development、WCAG 2.2 AA、WAI-ARIA Authoring Practices、Testing Library、Playwright、real-entry 验证，以及 Agent-Jarvis 账号登录与 OpenAI、DeepSeek、本地模型等 third-party provider authorization 的边界分离。

进入 UI 实现前，必须通过：

`powershell
python tools/governance.py ui
python tools/governance.py gate g1
`

声明 UI 任务完成前，必须具备当前通过证据，并至少覆盖：

`powershell
npm run test:auth-ui
npm run test:visual
npm run test:e2e
python tools/governance.py verify
`

`docs/UI_STANDARD.md` UI-GOV-001 的可执行强制实现是 `scripts/ui-contract.mjs`（静态层由 `npm run test:visual` 运行，真实浏览器层用 `node scripts/ui-contract.mjs --live` 运行）。任何 FAIL 阻断 UI 任务完成声明。

## 7. 复盘固化控制

每轮功能审查或运行反馈（P6）发现的实现缺陷，必须在闭环 CR 中同时产出：

- 自下而上的“观察 → 根因”表，根因指向流程/控制缺口而非仅指向单个 bug。
- 针对根因的可执行控制（规范原则、测试矩阵规则、或 `tools/governance.py` 检查）。
- 每条修复绑定真实入口证据。

参考记录：`project/05_evidence/EV-2026-09-08-functional-review-retrospective.md`。
