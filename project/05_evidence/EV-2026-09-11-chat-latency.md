## 1. 对话慢：我们自己只占 80 毫秒

在**同一个请求内**打时间戳，避免用两次独立请求对比而被 Provider 的波动欺骗：

| 时间点 | 第 1 次 | 第 2 次 |
|---|---|---|
| 进入处理函数 | 0 ms | 0 ms |
| 出站 fetch 已发出 | 74 ms | 85 ms |
| **DeepSeek 返回响应头** | **4,430 ms** | **6,248 ms** |
| 客户端看到首个 delta | 4,432 ms | 6,250 ms |
| 流结束 | 4,624 ms | 6,536 ms |

从响应头到客户端可见首个 delta 只隔 **2 ms**——SSE 管道没有缓冲问题。服务端全部自有开销（会话鉴权、技能与知识计数、历史装配、预算判定、上下文组装）合计约 80 ms。

服务端上下文处理单独计时（真实历史 68 条消息 / 173,741 字符）：

| 环节 | 耗时 |
|---|---|
| `estimateMessagesTokens` | 7.3 ms |
| `planCompaction` | 4.5 ms |
| `assembleContext` | 3.5 ms |

合计约 15 ms，不是瓶颈。

## 2. 一个被自己推翻的中间结论（教训）

排查中途曾得出「我们的 adapter 比直连慢 2 至 4 秒」的结论，**这是错的**，原因是两侧的计时标记不可比：

- 直连测量把「第一个含 `"content"` 字样的 SSE 帧」当作首字，而 DeepSeek 的首帧是 `{"delta":{"role":"assistant","content":""}}`——**content 为空**；
- adapter 的 `normalizeOpenAICompatibleChunk` 要求 `text.length > 0` 才产出 delta，标记的是第一个**真实字符**。

改成两侧都取「第一个非空 content」后复测，同一请求体：

| 路径 | 响应头 | 首个真实字 |
|---|---|---|
| 直连 | 734 ms | 1,401 ms |
| **我们的 adapter** | 632 ms | **1,058 ms** |
| 直连（复测） | 432 ms | 1,272 ms |

adapter 没有额外开销。**教训**：跨两套代码比较延迟时，必须先确认两侧标记的是同一个事件。

## 3. 两个被排除的嫌疑，与真正能控的那一个

### 排除：`max_tokens`

`CR-20260911-web-reading` 当天刚加了输出上限参数，是最自然的怀疑对象。交叉对照三轮（每轮内顺序执行三种请求体，消除时间漂移）：

| 轮次 | max_tokens=8192 | 不带 max_tokens | max_tokens=1024 |
|---|---|---|---|
| 1 | 688 ms | 622 ms | 625 ms |
| 2 | 623 ms | 660 ms | 611 ms |
| 3 | 636 ms | 602 ms | 591 ms |

无差异。该改动不背这个锅。

### 排除：工具定义数组

13 个真实工具定义（请求体 3,640 B）对照无工具（96 B）：首字 606 ms 对 731 ms，带 `stream_options` 时 449 ms。无差异。

### 主因：DeepSeek 自身波动

同一请求体的响应头时间在一天之内于 **432 ms 到 6,248 ms** 之间来回跳，取决于其服务端负载。这部分我们控制不了。

### 能控的那一个：每轮重放的历史

`assembleContext` 只在**超预算时**才套用保留窗口，而 REQ-F-041 ① 写的是「只有最近 N 轮的工具结果以原文保留」，**没有任何预算前提**。后果是没超预算的会话每轮把历史上所有工具结果原样重发：

| 会话 | 消息数 / 轮数 | 改动前每轮发送 | 套用保留窗口后 | 省 |
|---|---|---|---|---|
| 「知识看板」 | 67 条 / 10 轮 | 61,760 tokens（占预算 80%） | 21,803 tokens | 65% |
| 「现在开始可以联网了吗」 | 370 条 / 57 轮 | 240,768 tokens | 24,923 tokens | **90%** |

第一个会话正好卡在预算的 80%——既不触发保留窗口（要超预算），也不触发压缩（阈值同为 80%），于是每轮原样重发 6.1 万 token。该会话 173,740 字符正文里 **168,555 字符是工具结果**（占 97%），用户与助手文本合计仅 5,185 字符。

工具循环内每一步都要重发一次完整上下文，所以这个浪费是按步数翻倍的。

## 4. 报告靠左：分层样式输给了文档自带样式

用 Playwright 量 iframe 内 `body` 的实际盒模型（视口 1440）：

| 项 | 值 |
|---|---|
| `x` | 0（贴左边） |
| `width` | 1152 px |
| `max-width` 计算值 | 1152 px |
| `margin-left` / `margin-right` 计算值 | **0 px / 0 px** |

`margin: 0 auto` 没有生效。原因是当前显示的报告是**模型生成的完整 HTML 文档，自带样式**，其中有 `body { margin: 0 }`：

- 我把宽度与居中写在 `@layer jarvis-base` 里的 `.jarvis-insight` 上；
- **未分层的样式无条件压过分层样式**，与选择器特异性无关；
- 于是文档的 `body { margin: 0 }` 取消了居中，而我分层的 `max-width: 72rem` 因为文档没有竞争声明而存活；
- 结果：1152 px 宽的列被钉在 1440 px 视口的左边。

这本身是「自带样式优先」这条设计意图的正确行为，错在把**布局约束**也放进了会被覆盖的那一层。

### 修正后实测

宽度与居中移入一条**不分层**、且注入在文档自身样式**之后**的 `body.jarvis-insight` 规则（特异性 0,1,1 压过文档的 `body` 0,0,1，无需 `!important`）：

| 视口 | 报告 x | 宽度 | 占比 | 左右留白 |
|---|---|---|---|---|
| 1920 px | 307 | 1,306 px | 0.68 | 307 / 307 |
| 1440 px | 230 | 979 px | 0.68 | 230 / 231 |
| 900 px | 0 | 900 px | 1.00 | 让出整宽 |

## 5. 设计决策与依据

| # | 决策 | 依据 | 门 |
|---|---|---|---|
| D1 | 保留窗口改为**无条件**套用，不再只作溢出兜底 | §3：REQ-F-041 ① 本就没有预算前提；实测省 65%–90% | 双向 |
| D2 | 溢出路径只剩「收窄后仍超限即报错」 | 压缩自身消耗 token 且无法保证终止（DEC-026 ⑥ 原意不变） | 双向 |
| D3 | 报告宽度与居中放进**不分层**规则，注入在文档自带样式之后 | §4：分层规则必输给文档的未分层 `body` 声明 | 双向 |
| D4 | 宽度取视口 **68%**，1024 px 以下让出整宽 | 用户明确要求 0.68；窄屏下 68% 不可读 | 双向 |
| D5 | 不用 `!important` | 靠特异性即可；文档内部一切仍归它自己管 | 双向 |
| D6 | **不为对话延迟做任何「优化」** | §1–§3：自有开销 80 ms，主因是 Provider 波动；做缓存或预热只会增加复杂度而不改善首字时间 | — |

## 7. 本 CR 依赖人工发现的风险

**保留窗口的副作用**（CP-1）：三轮以前的网页正文对模型不再可见，只剩一行「结果已省略」。机器守得住「旧结果被省略、近 N 轮保留原文、用户与助手文本不受影响」；「某次追问恰好需要更早的工具结果」只有真实使用才会遇到。需要长期留存的内容应存入知识库——这正是知识库存在的理由。

**报告观感**（CP-3）：机器守得住宽度比例、居中、窄屏让宽与层序；「68% 在你的显示器上好不好看」由真实使用判断，比例值可按反馈调整。
