## 1. 目标与非目标

**目标**：把展示屏从一块静态标题屏，变成一块能回答「外面变了什么、我们手里有什么」的看板；知识库从扁平条目变成按实体索引的原始材料库；上层对话 Agent 能从中取材回答或整理报告。

**非目标**（写下来是为了挡住后续膨胀）：

- 不做项目交付跟踪（用户 2026-09-11 明确：客户层面「不涉及项目交付」）
- 不做客户健康分、流失预测、商务管道
- 不做趋势图表与数据分析；看板只呈现状态与存量
- 不做自动巡检（成本未测，另立 CR）
- 不做多人协作、分派、评论
- 不做费用与报价

## 2. 展示屏状态机

现状是两态：`home`（标题）与 `insight`（洞察 HTML，无沙箱 iframe，DEC-015 已接受风险）。本方案改为三态。

| 态 | 内容 | 进入 |
|---|---|---|
| 标题 | 现有标题视图 + 科幻动画 | 本次会话首次加载 |
| 看板 | 知识看板 | 动画结束、或 3 秒到时、或任一输入 |
| 洞察 | 报告 HTML | 模型调 `save_insight` |

**切换规则**（用户 2026-09-11 拍板 + 三条派生约束）：

1. 标题态是**开场，不是静息态**。静息态是看板。
2. **3 秒是上限不是固定时长**。任一输入立即切入：鼠标移动、键盘、滚动、点击，不限于移到标题或展板。
3. **只在本次会话首次加载播放**。之后直接进看板。理由：一天开二十次就是一分钟在看同一段动画。
4. **切换不得由动画结束事件驱动**。`globals.css` 有全局规则，用户要求减少动效时动画时长被压到 0.001ms；若切换等的是 `animationend`，关闭动效的用户可能卡在标题屏。切换由计时器与输入事件驱动，动画只是同时在演。
5. **洞察态优先于开场动画**。展示屏正显示报告时刷新，仍显示该报告，不播开场。开场只在静息态是看板时播。
6. 回到标题由既有 `show_home` 工具承担，**不做自动回退**（看着看着视图自己变了是更糟的体验）。

**待合并**：「鼠标进入工作区」的具体判定，与并行 CR 的「对话面板悬停态」合为一条规则。

## 3. 实体模型

一张实体记录，三种 kind，共用结构，状态字段按 kind 分化。**标准与监管接入机构合并为一类**（用户 2026-09-11：并网标准就是 TSO/DSO 所发，分开列会让同一件事出现两次）。

| kind | 建议命名 | 固定显示 | 状态字段 |
|---|---|---|---|
| 友商 | 友商 | Top N，顺序固定不重排 | 有无未读变更 + 一行变更摘要 |
| 规则与准入方 | **不叫「行业」** | 全部 | 下一个日期、在跟踪的规则数、可选的容量与队列 |
| 客户 | 客户 | 全部 | 容量、其发布的商业白皮书与技术准入要求 |

**命名注记**：这一类不要叫「行业」。标签太宽会变成垃圾桶，三个月后里面会混进行业新闻与分析师报告。建议「规则与准入方」或「准入方」——共同点是「给你定规矩、发许可的一方」。标签本身是一层 schema。

**客户是唯一有两面的一类**：技术面（白皮书、技术准入要求）与友商同构，都是变化检测；商业面只记容量，不做阶段评分。原因是没有交付数据，健康分背后没有东西。

**一个机构可能同时有多条规则在不同阶段**，一张卡塞不下多个阶段条。卡上只显示汇总（「跟踪 5 条，其中 2 条有阶段变化」），点进去才是清单。这是竞品情报工具的 battlecard 常规做法：卡片概览，详情页枚举。

## 4. 采集健康度

三类实体共用，与内容变化**分开显示**。五态：

| 状态 | 含义 | 该做什么 |
|---|---|---|
| fresh | 采集正常，对方确实没动静 | 无 |
| stale | 采集链路在，信息已旧 | 确认对方是否真沉寂，或换源 |
| failed_fetch | 拿不到页面 | 看连续失败次数 |
| parse_failed | 抓到页面但取不出内容 | 重配取数方式。**最危险**：页面还在更新，我们什么也没看见 |
| 未接入 | 从未配过源 | 配源，或明确标为「只手工维护」 |

**这一条是全案最要紧的一处**。没配源的卡片和对方真没动静的卡片，看上去都是安静。本项目已踩过同一类坑：`CR-20260911-tool-availability` 把「未探测」当成「不支持」，导致联网搜索根本调不起来。沉默不等于正常。

业界依据：竞品情报领域反复强调，监控漏掉一个对象或抓取延迟时，界面会用完全相同的自信外观呈现一张残缺的图，而读者看不出缺口。实践中的标记就是 fresh / stale / failed_fetch / parse_failed 四态。

## 5. 知识库是原始材料

用户 2026-09-11 定性：「知识库是原始材料。」这句话的后果比字面大。

1. **模型写入的语义变了**：`save_knowledge` 不是「模型总结一段然后提议入库」，而是「摘录一段原文，附上出处」。模型自己写的话不进库。
2. **报告是派生物**：进洞察，不进知识库，除非用户明确要求存。
3. **派生物不得回流成原始材料**。否则模型读到自己上一轮的总结再总结，一轮轮消化自己。这与 D 期「唤醒提醒绝不回放进上下文」（DEC-040 ④）是同一条规则换了个位置出现。
4. **证据规范因此简化**：原始材料的证据就是出处本身。真正需要单独立证的只剩**从文档抽出的结构化字段**（容量、窗口日期、阶段），那是二手值，必须能指回原文的哪一段。

**存储形态**（回答用户「采用链接保存以节省空间」）：省空间不是真问题，几千条 Markdown 正文只有几十 MB。真问题是两个：只存链接则检索不到（BM25 需要正文在本地），且链接会失效，尤其官网改版——而那恰是最需要留证的源。所以三件事分开：

- **存抽取的正文**：可检索、不失效
- **存原始链接**：可回源、是证据
- **不存原件**：PDF 等二进制默认不留，需要时按链接回源

**索引结构**：实体为主分类，文档类型为次分类，另设**「无归属」桶并显示数量**（学术论文、内部笔记、通用规格书没有实体归属；不显式留桶它会变成第二个垃圾桶，与「未分类」重复）。

**缺口信号**沿用既有结论：以**搜索无结果**为主（需求侧），覆盖矩阵为辅（供给侧）。`search_knowledge` 返回空的查询词就是按真实需求排好序的待补清单，几乎不需额外开发。

## 6. 写入与证据规则

| 规则 | 内容 |
|---|---|
| 没有就没有 | 信息准确性优先于完整性。缺就是缺，不猜、不补 |
| 模型只能提议 | 实体与字段更新经待采纳区，用户采纳后才生效（沿用 C 期 `pending/` 机制） |
| 官网可自动写入，但判据在工具里 | **「什么算官网」必须是实体上登记的源白名单，由工具校验，不能由模型自称**。否则模型在任意页面上宣称来源可信即可直接写库，「必须有证据」就空了 |
| 二手值必须可回溯 | 抽取出的字段记录值 + 来源链接 + 原文定位 + 抽取时间 + 方式 |

## 7. 操作逻辑（用户 2026-09-11 拍板）

1. **点开卡片上的某条新信息即算已读**（不做显式标记按钮）
2. **卡片点开是该卡片的消息列表**（不是详情表单）
3. **实体在对话里由模型建，建好进待采纳区**
4. **卡片详情内含源管理**；工具与技能的调用**不放进卡片**——那会让卡片变成第二个应用，与对话框重复，且步骤流与状态灯都在对话框里，卡片再来一套是两套真相。折中：卡片放一个入口，把问题预填进对话框，执行仍在对话里。

### 8.2 实测：工具预算与一处既有缺陷

本机实测（`buildRegistry` 全量注册，skillCount 3 / knowledgeCount 5 / 联网开）：

| 项 | 数值 |
|---|---|
| 当前工具数 | 11 |
| 工具目录文本 | 332 token |
| **发给 Provider 的 `tools` 数组** | **857 token** |
| 单工具目录均值 | 30 token |
| `toolDefinitions` 子预算 @ 8192 窗口 | 655 token |
| `toolDefinitions` 子预算 @ 128k 窗口 | 10240 token |
| 加到 22 个后的目录文本（外推） | 约 660 token |

**两个结论**：

**① `BUDGET_SHARES.toolDefinitions` 声明了但从未被执行。** `grep` 确认该常量在 `src/` 内除定义处外无任何引用；技能名录有 `renderSkillCatalogue` 按 `budgetTokens(window, BUDGET_SHARES.skillCatalogue)` 截断，工具目录没有对应处理。REQ-NF-007 ② 写明「子预算：技能名录、**工具定义**、单条工具结果、来源列表各有上限」——这一条目前是纸面约束，没有实现，也没有测试。**这是一处既有缺陷，不是本方案引入的**，但本方案会让它显性化。

**② 真正的成本在 `parameters`，不在 `description`。** 目录文本 332 token，而实际发出的 `tools` 数组 857 token，差额全在参数 schema。所以省 token 的办法不是把描述写短，而是把参数写简。按此，加 11 个工具后 `tools` 数组约 1700 token，是 8k 窗口子预算的 2.6 倍——**本地小模型装不下全量工具集**。

**更正**：上一轮口头讨论时我按每工具约 180 token 估算，说「20 个放不下」。实测单工具目录只有 30 token，那个数字是错的。结论（需要分组注册）不变，但理由变了：瓶颈是参数 schema 与 wire 体积，不是描述文本。

**建议**：工具按上下文分组注册——管理类工具（建实体、配源）只在展示屏处于看板态时注册。这与现行「没有技能就不注册技能工具」「知识库为空就不注册检索工具」是同一条规则的延伸，不新增机制。另外把 `toolDefinitions` 子预算真正实现并加断言，属另一个小 CR 的范围。

### 8.3 已落地的两个工具，和它们各自的判据

| 工具 | 落点 | 判据落在哪 |
|---|---|---|
| `fetch_source` | TASK-125 / `src/lib/sources.ts` | 只许采集该对象**已登记**的源；失败不推进 `checkedAt` |
| `ingest_url` | TASK-126 / `src/lib/ingest.ts` | 来源同域直入、否则待采纳；`trustCaller` 只给用户自己贴的链接 |
| `extract_fields` | TASK-127 / `src/lib/extract.ts` | 引文须在条目中逐字存在，且值须在引文之内；信任判据同上 |

两处刻意做成一件事的地方：

**①「可读」只判一次。** 采集要判「抓到了但取不出正文」，入库要判「这页值不值得存」，本是同一个问题。分开写迟早会出现一边认为抓到了、另一边认为没抓到的状态。所以 `fetchReadable` 从 `sources.ts` 抽出来给两边共用，阈值只有 `MIN_READABLE_CHARS` 一个。测试夹具低于这个阈值时，改的是夹具不是阈值——不为了让测试过而挪生产线。

**③抽取的证据改成可核对的。** §12.3 说过，抽错一个容量数字，看板上和抽对了长得一模一样。抽取本身只能由模型做，但它交上来的证据可以机器核对：条目必须在本地、引文必须在条目正文中逐字存在、值必须出现在引文之内。第二条挡住凭记忆的伪造引用，第三条挡住更隐蔽的一种——句子是真的，数字在誊写途中飘了。这两条都挡不住「读错了上下文」，那仍然是人的事；但看板上每个字段至少能追到本机上的一段文字。

**一处按真实失败改了实现**：空白最初做折叠（连续空白压成一个空格）。CJK 句子里的换行一折叠就多出一个原文没有的空格，诚实的引用因此被判成伪造。改成直接去除空白——被比对的断言本来就是「这段文字在那篇文档里」，与空白无关。

**②信任判据只有一处。** 入库沿用字段修改那条规则：来源 host 与该对象已登记源同域才直接进库，否则进待采纳区。`trustCaller` 是唯一的例外，留给用户在界面上自己贴的链接——这道闸门防的是模型把一页来路不明的东西说成事实，不是防人。`ingest.ts` 与 `entity-proposals.ts` 一样不自己解释 URL，判据留在调用方。

**一处已知抖动（记在这里免得下次当回归查）**：整套测试并发跑满时，`compaction` 与 `display` 里三个 SQLite 用例偶发触顶 5s 默认超时；单独跑 2s 内通过，复跑全量 496/496 全绿。再现时应调这两个文件的 `testTimeout`，不要动实现。

## 9. 需要的技能

技能是拿工具干活的说明书。**优先级按下表，纪律类先于领域类**。

| 优先 | 技能 | 内容 |
|---|---|---|
| 1 | **知识条目规范** | 一条知识多长、标题怎么起、何时拆成两条、实体与文档类型怎么填、什么不该入库 |
| 1 | **证据规范** | 什么算证据、来源怎么记、哪些情况可自动写入、拿不准时怎么标注而不是猜 |
| 2 | 竞品跟踪 | 哪些页面值得配源、一条变化值不值得记、变更摘要怎么写 |
| 2 | 并网规则跟踪 | 怎么读运营商公告、阶段词怎么映射、窗口日期在哪找 |
| 2 | 客户技术准入解读 | 白皮书里哪些是硬要求、怎么抽成条目 |
| 3 | 报告生成 | 报告结构、必须引用来源、不确定处怎么显式标出 |

**为什么纪律类必须先写**：§8 那批工具做的事是提高写入速度。没有前两本，工具建得越多，垃圾进库越快。用户定的「没有就没有」要靠证据规范落成可执行判据，否则它只是一句态度。

## 13. 主轴之争：容量 vs 技术要求（2026-09-12 定向）

用户否掉了容量主轴，理由是岗位视角：**技术方，不是市场方**。这一条推翻的不只是一个汇总条的算法，而是「这块看板到底在回答什么问题」。

- **容量主轴回答的是**：我们的盘子有多大、走到哪一步了。这是商务与经营的问题。
- **技术主轴要回答的是**：**别人要求什么、别人做到了什么、我们对不对得上。**

三类跟踪对象在技术视角下的共同度量不是容量，而是**带值的技术要求**：

| 对象 | 它提供的技术事实 |
|---|---|
| 规则与准入方 | 强制要求（并网限值、保护定值、故障穿越、谐波、通信规约、认证型号） |
| 客户 | 准入门槛（硬指标、必备认证、测试项） |
| 友商 | 已达成的水平（参数、已拿到的认证、公开的测试结果） |

于是主轴是一张**要求—参数对照**：每一条要求有名称、值、单位、来源对象、证据；我方状态只有三种——满足 / 不满足 / 未知。顶部汇总随之变成「**N 条要求未对上，其中 M 条卡在认证**」，而不是「锁定了多少 GW」。

**为什么这条比容量更可能收得齐**：容量数字散在公告与商务口径里、口径还互相不兼容；而技术要求本来就是**写在规范与准入文件里、带数字带单位、白纸黑字**的东西——这正是 `ingest_url` + `extract_fields` 那条链路最擅长抓的形状，逐字引文核对也只有在这种文本上才真正有力。

**代价（尚未实施，等用户拍板）**：

1. 实体的字段白名单（`UPDATABLE_FIELDS`，7 个固定字段）容不下任意命名的参数。需要给实体加**可重复的具名参数行**（与 `source` / `evidence` 同形，仍是文件，无表无迁移，双向门）。
2. 看板卡片的次要位置现在给了 `capacity` 芯片；技术主轴下那个位置应换成「未对上的要求数」。
3. `extract_fields` 的 `field` 参数目前只收白名单；要放开到具名参数，同时保留三道证据核对不变。
4. 技能里的《客户技术准入解读》《并网规则跟踪》本就按硬要求写，可直接复用；《竞品跟踪》要把「值得记的变化」重心从商务动作移到参数与认证。

**四条都已结清**（2026-09-12）。剩下的不是「未决」而是「只能靠用起来才知道」，见 §12 与各 CR 里如实登记的真实入口项：开场三秒是长是短、参数的三态够不够用、卡片密度、以及采集源会不会被对方当成爬虫。

## 12. 依赖人工发现的风险

1. **策展负担**。竞品情报平台（Klue、Crayon）公开的设计前提都是背后有专职的竞争情报或产品营销负责人做策展、调告警、维护卡片。本系统只有一个用户加一个模型。策展要么交给模型，要么看板会在两周内退化成一堆陈旧卡片。**这是全案最脆的地方，比任何布局选择都重要。**
2. **检索质量**。BM25 是词面匹配，同义改写检不到。机器只能守「含关键词的条目排第一」，「该检到的没检到」只有真实使用才发现。
3. **抽取准确性**。`extract_fields` 抽错一个容量数字，看板上就是一个错误的事实，且看上去和正确的一模一样。证据链（值 + 链接 + 原文定位）是唯一的兜底，必须强制。
