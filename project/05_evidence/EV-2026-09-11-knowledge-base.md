## 1. 检索方案实测（本 CR 选「零依赖 BM25 + CJK 二元切分」的依据）

C 期的核心取舍是：**要不要为检索引入依赖**（向量库 / 分词库 / SQLite FTS 扩展）。架构约束把「新增运行依赖」定为 L3，所以先量一下不引入依赖能做到什么程度。

语料：本机真实会话里长度 > 300 字符的助手消息，取最近 57 条，共 21,005 token，平均 369 token / 条——正好是「一条知识条目」的量级。对每条消息，取其中间一句（12–40 字）作查询，看能否把它自己检回来：

| 查询形式 | Top-1 命中 | Top-3 命中 | 说明 |
|---|---|---|---|
| 整句（12–40 字） | **55 / 56** | — | 唯一失手的一条是两段近乎重复的模型回复 |
| 只取句首 6 字 + 句尾 6 字 | **50 / 56** | **53 / 56** | 更接近用户「记得大概是什么」的真实查法 |

| 延迟 | 数值 |
|---|---|
| 单次检索 P95 | 12.6 ms |
| 单次检索最大 | 19.5 ms |

（57 篇 × 369 token 的全量在内存扫描，无任何索引结构。）

### 结论

- **零依赖够用**。几十到几百条笔记的规模上，60 行 BM25 + 二元切分的准确率与延迟都不构成问题；引入向量库或分词库会把本 CR 从标准档推到重型（L3 依赖 = 单向门），换不回相称的收益。
- **CJK 二元切分是关键**，不是可选项：中文没有空格，按「词」切需要词典（依赖），按「字」切区分度不够；二元是无词典条件下的最优折中，实测整句 98% 命中证实了这一点。
- 若日后条目上千、或需要语义近似（同义改写）检索，再另立 CR 评估向量方案——那时会有真实语料而不是推测。

### 复算方法

一次性测算，`node:sqlite` 只读打开开发库，`SELECT content FROM messages WHERE role='assistant' AND length(content) > 300 ORDER BY created_at DESC LIMIT 120`；查询句按 `[。！？\n]` 切分后取中位、过滤 Markdown 标记行；`tokenize` / `rankBm25` 即 `src/lib/knowledge.ts` 导出的同一实现。

## 4. 本 CR 依赖人工发现的风险

**检索质量**（CP-2）：BM25 只做词面匹配，同义改写检不到；机器守得住的是「含关键词的条目排第一、片段含命中词」（TEST-085），「用户觉得该检到的没检到」只有真实使用才发现。

**模型提议的取舍质量**（CP-6）：模型可能提议无价值或错误的知识；机器守得住的是「提议只进待采纳区、采纳前不可检索」（TEST-086 ⑤、TEST-089），提议是否值得采纳由用户在采纳时判断——这正是待采纳区存在的理由。
