# EV-2026-09-11-scheduled-sweep

- 对应变更: `CR-20260911-scheduled-sweep`
- 目的: 定时巡检的**成本先实测，再定形状**——这是 B / C 期定下的做法，也是 `CR-20260911-home-dashboard` 出口义务 5 里「定时巡检的成本仍需先实测再定」那句话的兑现。

## 1. 实测：一轮巡检花掉什么

本机测量，36 个源（12 个对象 × 3 个源的形状），每页 18 KB HTML，抓取以本地桩替代：

| 项 | 数值 |
|---|---|
| 一轮源数 | 36 |
| 首轮本地处理 | 308 ms |
| 次轮本地处理（有基线可比对） | 289 ms |
| 单源本地处理 | **约 8 ms** |
| 快照占用 | **约 17.9 KB/源**（上限由 `MAX_SNAPSHOT_CHARS` 20 万字符封死） |
| 单页响应上限 | 2 MB（`MAX_SOURCE_BYTES`） |
| **模型 token** | **0** |

测量脚本是一次性的，测完即删；数值来自 `fetchSource` 的真实代码路径（抽正文 + 按行比对 + 写快照 + 写回健康度），只有网络那一层是桩。

## 2. 那个 0 决定了设计

主动唤醒（D 期）要防的是 token 花销，所以它有**日 token 预算**。巡检一个模型调用都没有——变更摘要是 `describeChange` 机械算出来的，不经过模型。**把日 token 预算照搬过来是装饰**。

真正的成本有两样：

1. **别人的服务器**。我们的本地处理只要 8 ms，等待全在远端。
2. **墙上时间**，因而也是「用户等多久才看到结果」。

于是闸门换成三道：**默认关、每轮条数上限、最小间隔 30 分钟**。没有一道是关于 token 的。

## 3. 三个刻意的选择

**① 顺序执行，不并发。** 一轮 36 个请求同时打出去，在对方看来与一次小规模攻击无异。本地既然只花 8 ms，并发省下的只是我们自己的墙上时间，代价是别人的服务器。一轮只取几个，一个一个来。

**② 游标轮转，不按「最旧优先」。** 采集失败**不推进** `checkedAt`（那个字段记的是「上次真的学到东西」，这是 TASK-125 定下的）。因此「最旧优先」会让一个坏掉的源永远排在队首，每轮都占名额，把别的源饿死。游标存在 `app_settings` 里，每轮从上次停的位置往后取——坏源照样会被重试，但不会卡住队列。

**③ 从没采集过的对象排最前。** 卡片上「他们很安静」和「我们根本没在看」长得一模一样，而从没采过的对象正处在后一种状态。它的沉默最容易被误读，所以它先走。

## 4. 计划只在看板可见时跳动

轮次由看板组件驱动，且只在页面可见时发起（`document.visibilityState`）。理由不是省电：**后台标签页替用户持续敲别人的服务器，是一件不该在用户不在场时开始的事**。这与 D 期唤醒「只在页面可见且用户安静时触发」是同一条纪律。

「立即巡检一轮」按钮可以越过开关，因为那是用户自己的动作——与 `ingest_url` 的 `trustCaller` 同一条理由：闸门防的是自动行为，不是人。

## 5. 按这些数字外推

若 12 个对象各配 3 个源、间隔 3 小时、每轮 6 个：

- 一天约 8 轮 × 6 = 48 次抓取，每个源约每 6 小时轮到一次。
- 真实页面按 100–500 KB 计，一天 5–24 MB 流量。
- 本地处理合计不到 0.4 秒。
- 模型开销：**0**。

结论：成本不构成障碍，**礼貌与误读才是**。因此上限设在礼貌一侧（最小间隔 30 分钟、每轮 ≤ 20），而不是设在成本一侧。

## 6. 仍依赖人工发现

1. **对方是否把我们当爬虫**。限流、封 IP、返回验证码页——这些会表现为 `failed_fetch` 或 `parse_failed`，但「因为我们抓得太勤而被挡」和「页面改版」在健康度上看不出区别。
2. **间隔到底该多长**。180 分钟是个有礼貌的默认值，不是测出来的最优值；哪些源值得更勤、哪些一周一次就够，只有用起来才知道。
