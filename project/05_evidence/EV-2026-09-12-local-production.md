## 1. 为什么要做：dev server 的内存是运行事故的直接原因

2026-09-11 至 12 之间，后台任务「启动 dev server」被系统因内存不足杀掉 **4 次**。每次底层 Next 进程都活了下来并继续对 GET 返回 200，但按需编译的路由开始返回 500，错误为 `Jest worker encountered 2 child process exceptions, exceeding retry limit`。用户侧表现为「删不掉 Provider」「优先级上下移动不生效」——看上去像业务缺陷，实际是服务半死。

`next dev` 的常驻内存在数十次热更新后持续增长：

| 时刻 | dev 常驻内存 |
|---|---|
| 重启后 | 772 MB |
| 20 分钟后 | 890 MB |
| 数小时后 | 2,828 MB → 峰值 3,806 MB |

整机 15,830 MB，事发时可用仅 2,486 MB（84% 已用），node 进程组合计 2,499 MB 为最大单项。

## 2. 生产构建的实测内存

同一套代码，`next build` 产物用 `next start` 运行，与 dev 并排跑：

| 运行方式 | 端口 | 常驻内存 |
|---|---|---|
| `next dev` | 3000 | **1,564 MB**（该时刻；峰值 3,806 MB） |
| `next start`（生产构建） | 3002 | **126 MB** |

后续复测为 dev 2,858 MB / prod 136 MB。**约 12 至 21 倍差距**，随 dev 运行时长拉大。

代价与限制如实记录：生产构建改代码后必须重新 `build`，没有热更新；构建本身约 5 至 7 秒。

## 3. 拦路问题：生产模式下所有 API 返回 401

首次尝试 `next start` 时：

| 路由 | 结果 |
|---|---|
| `/` | 200 |
| `/api/providers` | **401** |
| `/api/display` | **401** |
| `/api/skills` | **401** |
| `/api/settings/search` | **401** |

原因在 `src/lib/auth-guard.ts`：`getNonProductionTestUserId()` 在 `NODE_ENV === "production"` 时直接返回 null。用户自 2026-09-09 起以 `JARVIS_TEST_USER_ID=admin` 的单管理员形态使用本应用（Google 登录暂缓，REQ-F-001 DEFERRED），而该旁路按设计不在生产生效。

### 为什么不放宽这个旁路

`JARVIS_TEST_USER_ID` 的名字与注释都写明它是**测试旁路**，「拒绝生产」正是它存在的意义。放宽它等于悄悄削弱一道守卫，且以后任何人把应用部署出去都会继承这个后门。

改为**新增一个语义不同的显式开关** `JARVIS_SINGLE_ADMIN_ID`：它陈述的是另一件事——「本实例没有登录，每个请求都是这个人」，这正是用户已经选择的形态。

### 安全边界：只允许开在本机

单管理员模式要同时满足两个条件才生效：

1. `JARVIS_SINGLE_ADMIN_ID` 被显式设置；
2. `NEXTAUTH_URL` 的主机名是回环地址（`localhost` / `127.0.0.1` / `::1`）。

第二条是防止免登录模式被开到公网的闸：一旦 `NEXTAUTH_URL` 指向真实域名或局域网地址，模式拒绝生效、请求回落为 401，强制走真实登录。`NEXTAUTH_URL` 缺失或无法解析时同样拒绝——判断不了就要求登录。

实测拒绝清单：`https://jarvis.example.com`、`http://192.168.1.20:3000`、`http://10.0.0.5`、`http://[2001:db8::1]`、`http://localhost.evil.com`（后者是 `localhost` 前缀的钓鱼域名，按主机名精确匹配被正确拒绝）。

## 4. 顺带查出的既有缺陷：预检脚本从不认识单管理员模式

`scripts/check-config.mjs` 在第 31 行计算 `const SINGLE_ADMIN = isRealValue(process.env.JARVIS_TEST_USER_ID)`，而 `.env.local` 由 `loadEnv()` 在第 89 行才加载。**常量在环境文件加载之前求值**，所以从 `.env.local` 配置的单管理员身份永远检测不到：

- Google 的两个变量始终被算作「必需」；
- 预检输出「缺少 2 项必需配置：GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET」；
- 退出码为 1。

即用户配置完全正确，预检仍报失败并指向两个这个模式根本不需要的变量。这与 `CR-20260909-config-preflight` 已记录的三个「诊断说谎」陷阱同属一类（`@next/env` 是 CJS、`__NEXT_PROCESSED_ENV` 缓存标记、`NODE_ENV=test` 不读 `.env.local`）。

修正后：Google 两项显示「暂缓」，退出码 0。

## 5. 设计决策与依据

| # | 决策 | 依据 | 门 |
|---|---|---|---|
| D1 | 新增 `JARVIS_SINGLE_ADMIN_ID`，**不放宽** `JARVIS_TEST_USER_ID` | §3：两者语义不同；放宽测试旁路会留下永久后门 | 双向 |
| D2 | 单管理员模式要求 `NEXTAUTH_URL` 为回环地址 | §3：唯一能在请求前判定「只有本机能访问」的现成配置信号 | 双向 |
| D3 | 判断不了（URL 缺失/非法）时**拒绝** | 安全默认值：不确定就要求登录 | 双向 |
| D4 | 真实会话优先级高于单管理员身份 | 配了真登录就该用真身份，模式不应遮蔽它 | 双向 |
| D5 | 生产构建用独立目录 `.next-prod` | `CR-20260909-next-build-dir-isolation` 的既有教训：构建产物不得与运行中的 `next dev` 共用 `.next` | 双向 |
| D6 | 修正预检的求值时机，并让它同时认两个开关 | §4 实测：否则配置正确也报失败 | 双向 |
| D7 | 预检显式提示两个 id 不一致 | 两者不同会让 dev 与生产看到两套数据，这个坑很隐蔽 | 双向 |
| D8 | **不做**自动重启 / 内存看门狗 | 治标不治本，且会掩盖真实的内存压力；本 CR 给的是一条内存低一个数量级的运行方式 | — |

## 6. 用户授权形态（如实记录）

助手在 2026-09-11 末尾提出：「要不要我把生产构建这条路走通？内存约为 dev 的三分之一，代价是改代码后要重新构建，而且要先把登录配好，因为免登录旁路在生产模式下不生效。」用户 2026-09-12 回复「**要。继续**」。

据此：新增开关、回环限制、构建与启动脚本、预检修正均为**明确授权**。D1–D8 的具体形态由助手代拟，全部为双向门，可单独撤回。

实测倍数（12 至 21 倍）高于助手当时给出的「三分之一」估计，该估计偏保守，已在本文件以实测数据更正。

## 7. 本 CR 依赖人工发现的风险

**长期运行下生产模式是否也增长**（CP-1）：机器守得住「刚启动时内存远低于 dev」；生产模式连续跑数天是否也会缓慢增长，只有真实使用才知道。

**重新构建的心智负担**（CP-2）：改完代码忘记 `build:local` 就会看到旧行为。机器守不住这件事——没有任何检查能区分「用户想看旧版本」和「用户忘了构建」。这是选择生产模式换取内存的直接代价，已写入文档。
