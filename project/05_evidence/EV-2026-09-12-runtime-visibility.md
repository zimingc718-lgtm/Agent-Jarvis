两件事看起来无关，其实是同一个：**运行时的状态对需要它的两方都不可见**。用户看到 `Failed to fetch`，判断不出服务是不是还活着；模型被问到接的是哪个模型，答「拿不到」——而那是实话。

## 1. `Failed to fetch` 的排查过程

### 1.1 逐项排除

| 怀疑对象 | 检查方式 | 结论 |
|---|---|---|
| 客户端误中断请求 | 读 `FloatingChat` 的 AbortController 用法 | 排除。每次发送新建 controller，有 `isStreaming` 防重入，无 effect 清理会中断它 |
| 服务进程崩溃 | Windows 事件日志近两天筛 node 相关错误与 Resource-Exhaustion | 排除。无记录 |
| Provider 调用挂死 | 读 `adapters.ts` 与压缩调用 | 排除。出网默认 60s 超时，压缩 30s 且 fail-open |
| 响应头被模型调用拖住 | 读 `createStreamingResponse` | 排除。`start` 事件在流一打开就入队，响应头随即刷出 |
| WSL 虚拟网卡（`172.31.96.1`） | 询问用户实际访问地址 | 排除。用户确认用的是 127.0.0.1 |
| 连接层本身不稳 | 实测（下） | 排除 |

### 1.2 连接稳定性实测

| 测试 | 结果 |
|---|---|
| 顺序 300 次 `GET /api/knowledge` | 300 成功 / 0 失败，4,016 ms |
| 并发 300 次 `GET /api/display`（12 轮 × 25） | 300 成功 / 0 失败，1,495 ms |

### 1.3 内存实测：不是泄漏，是整机压力

服务进程连发 1,200 次请求前后：

| 阶段 | RSS |
|---|---|
| 起始 | 567 MB |
| 第 1 轮 400 次后 | 568 MB |
| 第 2 轮 400 次后 | 568 MB |
| 第 3 轮 400 次后 | 568 MB |

**没有按请求泄漏**，567 MB 是平台期。

整机按进程名汇总（15.5 GB 物理内存，可用 1.5 GB，已用 14 GB，约 90%）：

| 进程 | 占用 | 个数 |
|---|---|---|
| claude | 1,952 MB | 17 |
| Code | 1,518 MB | 18 |
| msedge | 1,345 MB | 21 |
| svchost | 851 MB | 92 |
| **node（Jarvis）** | **656 MB** | **3** |

**吃得最多的是 Claude Code 自己，Jarvis 排第五。**如实记录：排查者本身是这台机器上最大的单一内存消耗方。

### 1.4 结论

`Failed to fetch` 是浏览器网络层的原始报错，含义只有一个：请求没连上，或连接中途断了。既然连接层与服务在存活时都稳定，那就是**请求发出时服务不在**。

当天已知的中断至少三次：系统因内存不足停掉过一个生产实例（后台任务通知在案）、助手为重建停过一次、重启一次。每一次都会让当时正在流式回复的对话报这个错。

**为什么查了这么久**：这个报错既不带时间，也不在任何地方留痕——服务端日志里什么都没有。这是本 CR 要修的第一件事。

## 2. 服务没有看护

`npm run start:local` 起完 `next start` 就不再管它。在 90% 内存占用下 Windows 会挑后台进程停，而它被停之后**就一直死着**，直到用户手工重启。

### 2.1 看护脚本的实测

停掉旧服务，改用 `npm run serve:local`，然后模拟系统杀进程：

```
起始健康检查: 200
子进程 PID: 17900
--- 模拟被系统杀掉 ---
重启后健康检查: 200
新子进程 PID: 29232
```

事件日志（`.data/server-events.log`）：

```
2026-09-12T14:55:24.219Z supervisor-started dist=.next-prod log=.data\server-events.log
2026-09-12T14:55:35.053Z server-exited code=4294967295 uptime=11s
2026-09-12T14:55:35.053Z restarting 第 1 次，1000ms 后
```

约 10 秒内自动拉起，PID 变化，健康检查恢复 200，且留下了带时间戳的记录。

### 2.2 为什么不是无限重启

一个起不来的服务（构建缺失、端口被占、配置有误）如果无限重启，会在后台无声空转。判定规则：**跑够 20 秒才退出算「被外部停掉」，重启并把计数清零；连续 3 次不到 20 秒就退出算「起不来」，停止并说明原因。**

清零这一条是关键：一晚上偶发几次内存杀，绝不能累积成「拒绝重启」——那正是这个脚本要防的故障本身。

该判定抽成了纯函数 `src/lib/supervisor-policy.ts` 以便单测；`.mjs` 脚本引不了 TS，所以里面是一份副本，并有一条断言挡住两边漂移（TEST-181）。

## 3. 模型说不出自己接的是什么

### 3.1 现状核对

| 位置 | 内容 |
|---|---|
| 身份提示 `DEFAULT_SYSTEM_PROMPT` | 一句英文：`You are Agent-Jarvis, a concise assistant running locally on the user's machine. Answer directly and keep prior turns of this conversation in mind.` |
| 易变后缀 `buildVolatileSuffix` | 只有 `当前展示屏：…` |
| 工具表 | 18 个，无任何自省类工具 |

所以 Jarvis 那句「我没有自检接口，拿不到当前接入的是哪家模型」**是实话**，不是它偷懒。

### 3.2 放在哪

放进**易变后缀**，不放稳定前缀。两个理由：

1. 它确实会变——用户可以在两轮之间换 Provider 或模型，REQ-F-040 的降级也会中途换人；
2. 放进稳定前缀会让每次换模型都重写前缀，把前缀缓存这件事本身毁掉（REQ-NF-008 ①）。

它不是时钟：只在运行时真的变了才变，没变的轮次一个字节都不动。

### 3.3 内容

一句话里同时给 **Provider 行的名字**、**类型**与**模型 id**，因为「是不是 DeepSeek」和「是不是我配的那个 DeepSeek」是两个问题，后者只有 Provider 名答得了。末尾附一句「用户问起接的是什么模型时，据此回答，不要说无法得知」——事实和指令都要给，因为它此前的默认反应就是说不知道。

## 5. 未覆盖的部分（如实登记）

- **根因不在代码里**。整机 90% 内存占用是真正的原因，本 CR 只让后果可见、可恢复。腾内存仍是收益最大的一步，而且不用改代码。
- **看护救不了「机器整体卡死」**。如果系统压力大到连重启都起不来，脚本会在 3 次短命退出后停下并说明——这是刻意的，但用户仍要自己处理内存。
- **报错文案的实际观感**未经真实使用检验。两种情形（服务不在 / 传输中断）的措辞是否让人知道下一步该干什么，只有真遇上才知道。
- **模型是否真的会照着运行时那行回答**属提示层，无法机器断言。机器守得住的是「那行确实发出去了、内容对、位置对」。
- **本 CR 不是 agent.md 层**。它只补了「运行时是什么」这一项事实，没有写工作顺序（本地优先、联网兜底）。那一环仍缺。
