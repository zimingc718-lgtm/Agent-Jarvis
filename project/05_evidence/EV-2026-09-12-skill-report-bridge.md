- 来源: 用户 2026-09-12「当前用 multi-agent-insight-reviewer 的 skill，做的报告输出 html 质量还不行，显示效果也不好，也没有渲染。检查这个功能有什么问题？」，助手给出四条处置后回「好的。按你的来，全做。」
- 时间: 2026-09-12
- 采集者: 助手（claude-opus-5），本机执行，数据取自用户真实会话与真实技能目录
- 支撑对象: `CR-20260912-skill-report-bridge`（REQ-F-140、DEC-120、TASK-200、TEST-200）
- 可定位路径: 本文件；`src/lib/tools/skill-tools.ts`、`src/lib/tools/display-tools.ts`、`src/lib/store.ts`、`src/components/FloatingChat.tsx`

## 1. 根因：技能不是为这个宿主写的

`multi-agent-insight-reviewer` 目录实测：

| 项 | 值 |
|---|---|
| 文件总量 | **167,755 字符**，20 个参考文件 |
| 自带 HTML 模板 | `assets/html-report-template.html`，3,327 字符，含 `<!doctype>`、`<head>`、`<style>` |
| 模板里的设计 | 品牌配色 `#1f4e79`、置信度色标（high/medium/low）、callout、figure/figcaption、表格样式、source-link |
| 产出流程原文 | 「Generate or update the final HTML or Word report artifact **directly**」，并让模型在 HTML 与 `.docx` 间二选一 |
| 提到 `save_insight` 的次数 | **0** |
| 提到 `insightId` 的次数 | **0** |

Jarvis 没有文件系统产出，没有 Word，唯一出口是 `save_insight`。技能对此一无所知，模型只能自己临场搭桥。

**还有一层放大**：技能 167,755 字符 → 注入上限 32KB → `read_skill` 再按 8,000 token 截断。模型实际看到的约为**五分之一**。

## 2. 后果一：报告章节乱序，而且只能乱序

用户真实会话里那份 7,809 字报告，标题按存储顺序是：

```
八、证据与参考 → 九、三方案比选 → 十、定制算例 → 十一、实施与运维
→ 1. 执行摘要 → 2. 方法 → 3. 背景 → … → 7. 工程要点
```

中文序号与阿拉伯数字两套编号并存。追查工具调用序列：

```
save_insight（新建）      1177 字  → 洞察 8991368c，开头是「八、证据与参考」
save_insight id=8991368c  3436 字
show_insight id=8991368c
save_insight id=8991368c  3194 字  → 用户说「1-7部分都没有」之后补的开头
```

模型把缺失的开头**追加到了结尾**。它没有别的选择：改动前 `save_insight` 只有「新建」和「追加」两种写法，**没有替换、没有插入、没有重排**。

同一会话里它还开了第二份洞察（先有 9af2a0ac 4,426 字，再有 8991368c），把一份报告拆成两份，而展示屏只显示较新的一份。工具当时对此没有任何提示，新建时只回一句「洞察已保存（id …）」。

## 3. 后果二：对话面板盖住报告的 78%

1440×900 实测：

| | 左 | 右 | 宽 | 高 |
|---|---|---|---|---|
| 报告列（68% 居中） | 230 | 1210 | 980 | — |
| 对话面板 | 336 | 1104 | 768 | 821 |

水平重叠 768 px = **报告列宽的 78%**，面板高度 821 px 对屏高 900 px。两者都居中，正好叠在一起。

指针移到展示屏时面板会收成底部 146 px 的输入条（实测：展开 top=79 高 821 → 收缩 top=754 高 146），指针移回面板内即恢复。机制是好的，但**默认状态下用户看到的就是被盖住的样子**。

## 4. 「没有渲染」其实渲染了

真实浏览器实测（沙箱化之后）：

| 指标 | 实测值 |
|---|---|
| `sandbox` | `allow-scripts` |
| body class | `jarvis-insight` |
| body 宽 / 视口 | 979 / 1440 = 68% |
| 左右 margin | 各 230.4 px（居中） |
| h2 字号 / 下边框 | 22.4 px / 1 px |
| 字体 | 已应用主题字体栈 |
| 页面错误 | 无 |

基础样式是生效的。用户感到「没渲染」，是因为看到的是**技能模板应有的样子与实际样子之间的落差**——置信度色标、callout、figure、品牌配色一个都没有，只剩通用排版；再加上被面板盖住大半。

模型产出的是光秃秃的 `<section>` 片段，**不含任何 `<style>`**（该洞察实测 `<style>` 出现 0 次）。技能自带的那套 CSS 从未随内容一起发出。

## 5. 顺带查出的一条死代码

`ChatDelta` 里有 `{ type: "insight"; insightId }`，前端 `FloatingChat` 也有对应分支（派发刷新事件 + 追加「已生成洞察，可在展示屏查看。」）。但全仓 grep：

```
src/lib/types.ts:59:  | { type: "insight"; insightId: string }
```

**只有类型声明，没有任何代码发出它。** 这是工具化之前「技能轮」路径的遗留，所以那句提示用户从未见过。本 CR 让三个写入路径都发出它，该分支随之复活。

这条是被 TEST-096 的真实入口断言逼出来的：新加的「报告落地后面板让开」挂在这个事件上，跑起来发现根本不触发。

## 6. 处置与验证

| 处置 | 落点 |
|---|---|
| `read_skill` 结果末尾附本机产出约定（唯一出口、一份报告一个 id、mode=replace、样式写进第一块、片段即可、编号统一） | `skill-tools.ts` |
| `save_insight` 增 `mode=replace` | `display-tools.ts`、`store.replaceInsightHtml` |
| 同会话重复新建时点名已有洞察的 id、体量与后果 | `display-tools.ts`、`store.listInsightsForConversation` |
| 报告落地后对话面板自动让开（流结束时，不打断流式） | `FloatingChat.tsx` |
| 三个写入路径发出 `insight` 事件 | `display-tools.ts` |

约定放在技能正文**之后**，这样即使被截断也削不掉它（TEST-200 ① 断言 `endsWith`）。也没有去改用户的技能文件——那个目录是用户的，重装技能会把我们的改动抹掉。

| 检查 | 结果 |
|---|---|
| `npx tsc --noEmit` | 0 |
| `npm test` | 642 用例 PASS（新增 7） |
| `node scripts/ui-contract.mjs` | 53 passed · 0 failed · 0 warnings |
| `npm run test:e2e` | **19 passed** |

期间出现过一轮 5 条 e2e 失败，经 stash 对照确认与本次改动无关：干净工作树上同一条同样失败，且失败点是 provider 保存与 DELETE 超时，整轮耗时由 2.7 分钟涨到 6.0 分钟。当时机器可用内存 1.5–1.8 GB / 15.5 GB。单独重跑各条均通过。如实记录，不归因于本 CR。

## 7. 未覆盖的部分（如实登记）

- **模型是否照做属提示层**。约定写清楚了，但它是否真的把 `<style>` 带进第一块、是否真的用 `mode=replace` 修顺序，机器断言不了。只能靠下一次真实使用检验。
- **技能仍有五分之四进不了模型**。167,755 字符对 32KB 注入上限，本 CR 没有改这个比例——那要么提高上限（挤占每轮预算），要么让技能可分文件按需读取，都需要单独评估。
- **面板让开只在有 hover 能力的设备上生效**，触屏不启用（沿用 REQ-F-054 ⑤）。
- **旧报告不会自动修复**。已经写坏顺序的那份仍在库里，需要让模型用 `mode=replace` 重发一次。
- **两者都居中这个结构性冲突仍在**。本 CR 用「落地即让开」绕过了默认状态下的遮挡，但用户若手动展开面板去看对话，报告依然被盖住。彻底解法是让两者不争同一条中轴，那是更大的布局改动。
