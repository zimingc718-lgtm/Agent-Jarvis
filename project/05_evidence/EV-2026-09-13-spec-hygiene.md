## 4. 为什么状态判据分级

`p1`/`p2`/`p3` 只报，`check release --strict` 才拦。

中途有半成品是常态：一条需求的任务刚 DONE、R1 刚终裁，状态列还没改，这在工作中不是错误。但**发布那一刻说明书必须说真话**——否则「到底做完没有」就只能靠人一条条翻，而那正是 2026-09-10 之后三天里发生的事。

反面教训就在眼前：DEC-210 ② 的「人的一侧」判据全表 92 行命中 4 行，当时选择只报不拦，理由是误伤率高。这条不一样——它的误报率实测为 0（26 条全部确实该推进），所以敢在 release 拦。**判据的形态由实测决定，不由我对它的喜好决定。**

## 5. 证据的局限

- **`check-req-status` 只认「任务全 DONE」**。一条压根没有任务实现它的需求（真正的追溯断链），本判据看不出来——它会因为「没有任务」而直接跳过。REQ-F-102 / F-130 / F-140 今天看起来正是这个样子，而真因是表格错列。两条检查合起来才照出这件事，单独任何一条都不够。
- **`check-tables` 只查列数**，列的含义排错了照样放行。
- **CP-3、CP-4 改的是纸面**，不改任何运行行为；它们的正确性由「改完之后两条检查全量 PASS」来证明，而不是由「我读过一遍」来证明。
