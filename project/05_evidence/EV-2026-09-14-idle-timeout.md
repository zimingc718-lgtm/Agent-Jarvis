# EV-2026-09-14-idle-timeout

- 来源: 助手 2026-09-14 为 `CR-20260912-turn-budget-continue` CP-3 逼一次输出截断时撞到；用户同日「继续」授权修复
- 时间: 2026-09-14
- 采集者: 助手（claude-opus-5），在用户自己那台服务器上执行（端口 3000，生产构建 + `serve:local`）
- 支撑对象: `CR-20260914-idle-timeout`（REQ-NF-061、DEC-290、TASK-370、TEST-370）；并完成 `CR-20260912-turn-budget-continue` CP-3 的真实入口
- 可定位路径: 本文件；`src/lib/adapters.ts`、`tests/adapters-stream.test.ts`

## 1. 一个被秒表挡住的功能

为了验「输出被截断后自动续写」，我让模型连续写一份长讲义。第一次的结果：

```
正文字数: 13499
[60s] error: Provider stream timed out.
```

**13,499 个字正在往外流，第 60 秒整条被掐断。**

`AbortSignal.timeout(60_000)` 量的是整条流的**总时长**——从创建那一刻起倒计时，不看有没有数据在来。于是「一直在产出的流」和「一个字都不出的流」被同一把尺子量。

同一把表当天早些时候还报对过一次：DeepSeek 上游返回 200 之后 60 秒零字节。**同一个数字盖住了两种完全不同的事**——一个该杀，一个不该。

## 2. 改前改后，同一条提问

| | 改前 | 改后 |
|---|---|---|
| 结局 | 第 60 秒 `Provider stream timed out` | 第 **127** 秒正常 `done` |
| 正文 | 13,499 字（被截断丢失） | **29,340 字** |
| 模型调用 | 1 次（未完成） | **3 次**：累计输出 8,192 → 16,384 → 17,841 |

## 3. 顺带验掉的 CP-3

改后那三次调用的形状本身就是证据：前两次的累计输出**正好顶满 DeepSeek 的 8,192 上限**（8,192 与 16,384 两个整数），第三次 17,841 自然收尾。

也就是说：**被截断了两次，自动续写了两次，全程无人输入「继续」**——`REQ-NF-060 ②` / `CR-20260912-turn-budget-continue` CP-3 的真实入口就此完成，`MAX_CONTINUATIONS = 3` 未触顶。

这条真实入口从 2026-09-12 挂到今天跑不成，原因不是「没时间」也不是「要花钱」，而是**它被另一个缺陷挡在门外**：任何能触发续写的长回答，都活不过那 60 秒。

## 4. 测试里栽的一跤

第一版的测试 ② 假绿：桩 `fetch` 没接 abort 信号，看门狗开了火，桩照样把数据吐完。真 `fetch` 会把中止传给 body 流，桩不接就等于**把被测的那条路绕开了**。

改成 `signal.addEventListener("abort", () => controller.error(...))` 之后才真的红/绿分明。

## 5. 局限（如实登记）

- **持续缓慢滴字的坏流可以无限期活着**。看门狗认字节，不认内容。止损该由 `max_tokens` 与本轮累计天花板（REQ-NF-060 ①）负责，不该由秒表兼任——这正是本次改动的理由本身。
- **连接测试仍按总时长**：`/models` 是一发一收的探测，没有「还在产出」这回事；两处统一成一种写法会让慢速网络下的连接测试永不返回。
- **CP-4（本轮累计触阈）仍未触发**：这一轮累计 54,324，离 DeepSeek 窗口下的天花板还远。
