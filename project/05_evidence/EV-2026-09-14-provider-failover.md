# EV-2026-09-14-provider-failover

- 来源: 用户 2026-09-14「若有时候 DeepSeek 作为优先级高的模型能力不足的地方，可由优先级不高的模型如 openai 执行，不一定全都是一个模型解决」
- 时间: 2026-09-14
- 采集者: 助手（claude-opus-5），在用户自己那台服务器上执行（端口 3000，生产构建 + `serve:local`）
- 支撑对象: `CR-20260914-provider-failover`（REQ-F-210、DEC-280、TASK-360、TEST-360）
- 可定位路径: 本文件；`src/lib/store.ts`、`src/lib/chat.ts`、`tests/chat-stream.test.ts`

## 1. 这条需求是从一次真实故障里长出来的

2026-09-14 白天实测：DeepSeek（优先级 0）上游返回 200 之后 **60 秒零字节**，同一句话指定 OpenAI **3.6 秒答完**。当时这一轮只会超时——**链上排着一个能答的 Provider，系统却不会去试它**。

`resolveActiveProvider` 只返回队首，「队首不行就换下一个」这件事在上层无从做起。

## 2. 三条边界

| 边界 | 为什么 |
|---|---|
| 只有**第一次**模型调用下沉 | 第二步及以后已经跑过工具，换模型等于重复副作用 |
| 只有**零可见输出**时下沉 | 已经吐字再换，用户会看到半句话被另一个模型接着写 |
| 每轮**最多一次** | 否则一条坏链能把一次提问变成 N 份账单 |

`usage` 不算可见输出——它在第一个字之前就到。白天那次超时的事件序列正是 `start → usage → error`，整整 60 秒没有一个 `delta`。

## 3. 单测四例（全绿）

`npx vitest run tests/chat-stream.test.ts` → 17 passed。

**第一版四条全红，而产品代码是对的**：断言看的是「传了哪个 model 字符串」，可首次调用本来就传 `undefined`（用该 Provider 的默认模型）。观察点改成「打到了哪个 baseUrl」之后四条全绿。**判据错了比实现错了更难发现——因为它红得很像真的。**

③ 断言的是「**不**换」：只写会换的用例，一个见失败就换的实现照样能过前两条。

## 4. 真实入口（用户自己那台服务器）

傍晚 DeepSeek 自行恢复（1 秒回答「2」），下沉路径于是不会自然触发。**碰巧没触发不等于验过了**，所以造一次真失败：把队首 DeepSeek 的 `base_url` 临时指向一个没人在听的端口，发一句话，验完立即还原。

```
事件: start → delta → usage → turn_usage → notice → done
[4s] 「DeepSeek」未能应答（Could not reach provider: fetch failed.），本轮改用「OpenAI」。
回复: 2
耗时 4.0s
已还原 baseUrl: https://api.deepseek.com
```

四件事同时成立：**换过去了**（OpenAI 作答）、**说出来了**（记录区里那句话）、**没把错误抛给用户**（全程无 `error` 事件）、**配置还原了**。

## 5. 顺带证实的两件事

1. **白天那次 60 秒零字节是 Provider 侧的问题，不是代码**：同一把密钥、同一条路径，傍晚 1 秒就回。当时用假密钥打同一端点 401 秒回，也指向这一结论。
2. **DEC-260 的修复在真实环境里生效了**：`providers.tool_support` 现在是 `{"gpt-5":"yes"}` —— 那是模型真的调起工具之后学到的结论，而不是一次失败被写成的 `no`。

## 6. 没验到的（如实登记）

- **换过去之后答得好不好**，机器判不了。断言只能证明换过去了、说出来了。
- **窗口更小的 Provider 接手长上下文**会在它那边溢出——要构造一条「在 A 装得下、在 B 装不下」的上下文才能验，**登记为人工发现项**，局限已写进 DEC-280 的风险列。
- **能力下沉（①）的真实入口没跑**：它要求队首被**探测为** `no`，而这台机器上两个 Provider 现在都不是 `no`。造一个假的 `no` 写进库能触发，但那是构造出来的状态，不是真实状态——单测四例已经覆盖该分支，此处不假装。
