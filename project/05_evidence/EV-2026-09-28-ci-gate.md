## 2. 设计与代码核对

- **工作流** `.github/workflows/ci.yml`：触发 `push`（`main`、`cr/**`）、`pull_request`、`workflow_dispatch`；`concurrency` 让同一 ref 的新运行取消旧的；`ubuntu-latest`，Node 24（`node:sqlite` 需要）+ Python 3.13（治理工具与 markitdown）；`npm ci` + `pip install -r requirements.txt`；六个步骤按本机 `verify:all` 的顺序：`test:typecheck` → `test`（vitest 全量，含 `tests/visual.test.ts` 与 UI 契约）→ `test:governance` → `governance:ci` → `test:ui-contract` → `build:verify`。少的只有 `test:smoke`——它要一台活服务。
- **治理 `ci` 阶段**：`STAGE_GATES["ci"]` = p3 去掉 `verify`。原因：CLOSED 翻状态那次提交晚于快照，`verify` 在 main 上会对那一个 CR 文件报 `BASELINE_CHANGED`，直到下一个 CR 的 snapshot 吸收它（[[governance-gotchas]] 里已登记的既定节奏）；托管 runner 守不了这一条，而合并时本机的 `verify` 仍守。其余评审门（r1–r4）、证据门（g1–g3.5）、结构与卫生检查一个不少；`gate g4` 只属于 `release`。`check ci` 在本仓库当前状态 PASS（第一次跑时因说明书行未落而报 `CHECK_IDS_DANGLING` / `INDEX_STALE`，落行与重生成索引后转绿——这正是该阶段该拦的事）。
- **拦截部署**：Railway 的「Wait for CI」是服务设置，`ServiceInstanceUpdateInput` 里没有对应字段（只有 `healthcheckPath` / `healthcheckTimeout` / `tracingEnabled`），API 设不了，只能用户在仪表盘点开。写进 CLAUDE.md §六 与 `docs/ARCHITECTURE.md` 部署形态，并在 R4 与测试说明书登记为人工发现项。
- **守卫**：`tests/ci-workflow.test.ts` 用文本断言逐步核对工作流（触发、运行环境、六步顺序、不含 smoke、npm script 指向 `check ci`），不引入 YAML 解析依赖；`CiStageTests` 钉住「`ci` = p3 − verify」的关系。
