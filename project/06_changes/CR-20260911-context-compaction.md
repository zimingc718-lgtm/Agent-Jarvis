- 方案选项:
  - A. **按轮数压缩**（超过 N 轮就把更早的压掉）——**被实测否决**。本机 9 个真实会话的测算显示：109 条消息的会话省 82%，但 18 条的**倒亏 19%**、10 条的**倒亏 11%**——摘要本身比它替掉的内容还贵。这会在小对话上原样重演 A 期 PM-1 的「token 不降反升」，只是换了一层。
  - B. **按预算触发 + 净省校验**（选中）——只在接近输入预算上限时压缩，且只在「被压内容显著大于摘要」时才真的压；否则维持原样并沿用 A 期的溢出路径。
  - C. 纯规则截断（直接丢最老的轮次，不调模型）——零成本、完全可预期，但模型是**彻底忘记**而非记模糊；用户在 Q2 选择了「用当前对话同一模型生成摘要」，即接受为质量付费。
- 选择理由: 选 B。①**证据优先**：方案 A 的缺陷不是推演出来的，是在用户本机 9 个真实会话上量出来的（EV §1）。②用户 Q2 选了「同一个模型」生成摘要，意味着每次压缩有真实成本，触发就**必须**保守——按预算而非按轮数，且带净省校验。③摘要**以消息行形式落库**（`role='system'` + `status='summary'`），复用既有列，**因此没有 schema 变更、没有迁移、没有单向门**；原始消息一律保留，压缩只影响「发给模型的上下文」。
- 回滚方式:
  - 运行回滚：`git revert` 本 CR 的实现提交。`budget.ts` 回到 A 期组装规则，`chat.ts` 去掉压缩触发，UI 去掉边界标记。
  - 数据：摘要以既有列的普通消息行存在（`status='summary'`），**无 schema 变更、无迁移**。回滚后旧代码读到这些行时，`REPLAYABLE_STATUSES` 不含 `summary` → 自动被过滤掉，行为退回全量回放，**不会把摘要当成真实对话内容外发**。如需彻底清除：`DELETE FROM messages WHERE status='summary'`。

## 角色意见

标准档只取与本 CR 直接相关的角色意见，不做完整四角色 R1–R4。

| 角色 | 意见 | 处理 |
|---|---|---|
| 产品 owner | ①「静默触发」与「摘要可展开」在用户答复里字面冲突（Q1 选静默、Q3 的选项文字提到「对话里那行『已压缩』」）。解读为「不打断阅读流 ≠ 不留痕迹」，落为 CP-4 的极轻分隔标记，并在交付时提请用户确认。②压缩带来的用户可感知代价——模型对早前细节由逐字变摘要——必须在需求里写明，不能当实现细节。③REQ-F-041 工具结果保留窗口与本 CR 的文本压缩是两条独立规则，不得合并，否则短会话会被压两次。 | CP-4 成文；REQ-F-042 验收写明记忆代价；REQ-F-041 保持不变 |
| 架构角色 | ①**用消息行承载摘要**（`status='summary'`）避免了新表/新列，把本可能是单向门的 schema 变更消掉了——这是本 CR 能走标准档而非重型的关键。②回滚安全性必须显式验证：旧代码的 `REPLAYABLE_STATUSES` 过滤会自然排除摘要行，须有断言（CP-9）。③摘要生成复用 `makeCompleter`（既有非流式调用路径，REQ-F-020 ② 已在用），不新增调用形态。④触发阈值与净省倍数按 DEC-018 `maxRatio` 先例：架构定初值，被实现或实测证伪则修订并回写。 | 立 DEC-030；CP-5/CP-9 成文 |
| 测试角色 | ①基准断言必须用 **EV §1 的真实会话形状**（109/78/28/18/10 条），而不是构造的理想数据——短会话倒亏正是构造数据发现不了的。②CP-2 的摘要质量**机器只能守结构**（非空、有界、含关键实体），语义准确性属真实入口，须如实登记为人工发现项，不得用一条宽松的机器断言伪装成已覆盖。③fail-open 必须有注入失败的用例，否则「压缩不得成为新失败点」只是一句话。 | TEST-079..083 按此设计 |
