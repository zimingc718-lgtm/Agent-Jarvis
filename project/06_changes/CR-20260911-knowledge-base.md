- 方案选项:

## 角色意见

标准档只取与本 CR 直接相关的角色意见。

| 角色 | 意见 | 处理 |
|---|---|---|
| 产品 owner | ①用户说的是「记忆」，记忆首先要**存得顺手**——所以三个人工入口（拖文件、点回复、往目录放文件）缺一不可，不能只给模型一个工具。②模型提议必须**可见且可拒**：一条提议进了待采纳区而用户不知道，等于没有审批。③知识库空时不要在提示词里占预算。 | CP-5/6/7 成文；CP-8 转录区提示；CP-3 按条目数注册 |
| 架构角色 | ①不建表是本 CR 能走标准档的关键（同 B 期 DEC-030 手法），代价是列表需扫目录——几百个文件级别可接受，并以目录签名缓存索引。②检索零依赖必须有实测而非「应该够」→ EV §1。③`ToolResult.events` 是通用侧通道（与 `sources` 同型），不是知识专用分支，循环核心不认识任何具体工具。 | 立 DEC-031；EV §1；CP-8 成文 |
| 测试角色 | ①待采纳区的核心断言不是「文件在 pending/」，而是**「采纳前检索不到」**——这才是审批机制的本体。②路径穿越要在名称层就消掉，并断言非法名读 / 删都得 404 而非走文件系统。③真实入口必须覆盖「模型提议 → 用户采纳」全链路，不能只测 API。 | TEST-086 ⑤ / TEST-084 ⑤ / TEST-087 ④ / TEST-089 ② 按此设计 |
