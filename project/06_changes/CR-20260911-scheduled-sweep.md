- 方案选项:
  - A. **服务端常驻定时器**（`setInterval` on the server / cron）——否决。本应用是本机单用户、按需启动的 Next 进程；常驻定时器意味着关掉界面后仍在替用户抓别人的网站，而用户看不到、也停不下来。回滚代价也高：它不随页面消失。
  - B. **看板驱动、仅在可见时跳动**（选中）。与 D 期唤醒同一条纪律：只在用户在场时花别人的资源；关掉页面就自然停止。
  - C. 每轮把所有到期源并发抓完——否决。本地处理只占 8 ms，并发省的是我们自己的时间，代价是对方服务器上一次突发；且失败时无法礼貌退避。
- 选择理由: 选 B。①**实测先行**：EV §1 量出模型 token 为 0，于是 D 期那套日 token 预算不照搬，闸门改为「默认关 + 每轮条数上限 + 最小间隔」，都落在礼貌一侧；②**门的形态**：设置是 `app_settings` 三个键，游标也是一个键，回滚即删键，无表无迁移；③**不新增出网面**：抓取复用 TASK-125 的 `fetchSource`，SSRF 守卫与逐跳校验原样生效。
- 回滚方式:
  - 运行回滚：`git revert` 本 CR 的实现提交。巡检条消失，`/api/entities/sweep` 消失，手动「立即采集」仍在（TASK-125）。

  - 回滚后重跑 `npm test`、`npm run test:ui-contract`、`verify | check-changes | check-doors | check-ids` 并重新 `snapshot`。

## 角色意见

标准档只取与本 CR 直接相关的角色意见。

| 角色 | 意见 |
|---|---|
| 产品 | 巡检要解决的是「卡片上的安静到底是谁的安静」。所以巡检条上必须写「还没有巡检过」，不能空着——空着会被读成「一切正常」。 |
| 架构 | 不要起服务端常驻定时器。这个应用是本机按需启动的；常驻定时器会在用户看不见的地方持续对外发请求，且随进程而非随界面存在，停不下来也回滚不干净。 |
| 模块开发 | 复用 `fetchSource`，不要另写一条抓取路径。SSRF 守卫、逐跳重定向校验、失败不推进 `checkedAt`——这些都已经在那条路径上，重写一遍就是重犯一遍。 |
| 测试 | 能断言的是选取与轮转（纯函数）、上限、默认关、不可见不发起。「会不会被对方当爬虫」只有连续真实运行能发现，CP-5 如实登记。 |
