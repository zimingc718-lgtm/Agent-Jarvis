- 方案选项:
  - A. 把看板做成第四个 `display_state` 值，存进库——否决。那会让「看板态」变成跨会话粘住的持久状态，`show_home` / `show_insight` 与它互相打架；而开场本来就是**本次会话**的事。
  - B. **看板是客户端的一个阶段，不进持久状态**（选中）：`view` 仍只有 home / insight 两种持久态，`stage` 是组件内的会话态。
  - C. 保留 `/dashboard` 作为长期入口——否决。两个入口意味着两套状态与两处要维护的布局，而出口义务写明接线完成即删。
- 选择理由: 选 B。①**洞察压过开场**：持久态优先级天然成立，不需要额外判断；②**一次会话只播一次**用 sessionStorage，新标签页会重放，符合「开场」的含义；③**切换不由动画结束驱动**：动画是循环的，若等它结束，慢机器停留更久而用户看不出原因。

## 角色意见

| 角色 | 意见 |
|---|---|
| 产品 | 开场只该出现在「刚打开、还没开始干活」的那一刻。任何表示开始干活的动作都应立刻跳过它，而不是让人等。 |
| 架构 | 不要把看板写进 `display_state`。那张表是「屏幕现在显示什么」的持久事实，而开场是会话里的一次性过程，两者混在一起会让 `show_home` 的语义变得不可解释。 |
| 模块开发 | 交接必须是事件，不能让看板直接调用对话框的方法。看板不知道问题写完没有，所以它只负责把话填进去。 |
| 测试 | LB-09 挡下了我原本要用的 keydown。那条规则护的是免责提示不可关闭，比我的方便重要；换成 `focusin` 两全。 |
