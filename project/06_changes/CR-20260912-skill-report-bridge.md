## 角色意见

| 角色 | 意见 |
|---|---|
| 产品 | 用户报了三件事，其实是一条链：技能不知道这里怎么出东西 → 模型瞎搭桥 → 出来的东西又被面板盖住。三处都要动，少一处用户还是看不到想看的。另外重复新建那条提醒一定要说**后果**，光说「已有一份」模型不会改行为。 |
| 架构 | 别去改用户的技能目录。那是他的文件，我们改了，他重装技能就没了，而且每来一个新技能都要再改一遍。附在 `read_skill` 结果后面是对的，而且要放在正文**之后**——正文会被截断，约定不能跟着被削掉。 |
| 模块开发 | `replace` 要和 `append` 并存，默认仍是 append，否则既有分块流程全得改。还有 `mode=replace` 不给 id 必须拒绝，不能默默当成新建。 |
| 测试 | 面板让开这条我坚持走真实入口。写完单测跑 e2e 才发现它根本不触发——`insight` 事件全仓没人发，前端那个分支是死的。这种「类型在、handler 在、就是没人发」的洞，纯函数断言永远照不出来。 |

## R1 人工终裁

以下 2 项记为**按助手建议采纳、待追认**，可单独撤回：

1. **不改用户的技能文件，改为在 `read_skill` 结果后附约定**。好处是技能目录保持原样、重装不丢、对所有技能一次生效；代价是每次 `read_skill` 多几百字符。若更希望把约定固化进某个技能，可另行处理。
