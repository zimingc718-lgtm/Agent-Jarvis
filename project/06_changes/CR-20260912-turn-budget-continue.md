## 问题陈述（证据，非主张）

**实测：一个问题累计 1,028,825 input token + 35,261 output token（约 1.6 美元），答案被输出上限截断在 768 字，提问的两半里只答了一半。**

机制（复核后）：`agent-loop.ts:105` 的循环在每次 provider 调用前跑 `fitToolLoopContext`，按 `budgetTokens(window, BUDGET_SHARES.totalInput)` ≈ 76.8k 判定，超了就按 `[3,2,1]` 只留最近几条工具结果，仍放不下才中止本轮。单次请求因此始终在预算内。

无界的是它上面那一层：`MAX_TOOL_STEPS = 100` 允许一轮内上百次调用，`addUsage` 逐次累加，而**没有任何一处在看这一轮的总账**；界面上（`SearchSettings.tsx:114-119`）也只有会话累计值。

输出侧：11 轮里 **5 轮**被截断。提示说「可以让我继续」但不会自动续写。gpt-5 的 reasoning token 吃掉大部分输出预算——有一轮 8192 output token 只换到 1,574 字可见正文。

信息损失：`narrowToolResults`（`budget.ts:286-295`）把被裁结果替换成裸常量 `OMITTED_RESULT`，而 `ToolResult` 已有 `summary`（步骤行在用）。模型综合时因此不知道自己读过什么。

**REQ-F-041　工具结果保留窗口（修订 ①，其余项不动）**

> 现行 ①：「发送给模型的上下文中，只有最近 N 轮的工具结果以原文保留；更早轮次的工具结果替换为一行摘要标记（工具名 + 参数摘要 + 「结果已省略」）；N 由架构定（建议 2）」。
> 修订为 ①：「发送给模型的上下文中，工具结果的保留同时受**轮**与**预算**两个条件约束：最近 N 轮之外的工具结果一律替换为占位；**在此之后若仍超出 REQ-NF-007 ① 的总输入上限，则在当前轮内从最旧的工具结果起继续替换为占位，直到落回预算内**。占位不再是纯标记，而是保留一行摘要（工具名 + 参数摘要 + 该次调用的结果要点）。N 由架构定（建议 2）。」
> 修订理由：现行条文按「轮」定义，单轮内 38 个工具结果全部落在「最近 N 轮」之内，**照条文逐字执行也不会裁任何一条**——这是条文未覆盖，不是实现走样。
> 注意：REQ-F-042 ⑦ 明写「与 REQ-F-041 的工具结果保留窗口是两条独立规则，不合并」，本次修订**不动 REQ-F-042**，两条规则仍各自成立。

**REQ-NF-060　单轮成本护栏与可见性（MUST）**

> 描述：一轮对话花掉多少必须看得见，且不能没有上限。
> 验收标准：①单轮 input 达到按 Provider 上下文窗口算出的比例阈值时，**停止继续发起工具调用**，改用已获得的材料作答，并在步骤流中说明原因；②输出因长度上限被截断时**自动续写至模型自然结束**，不再要求用户输入「继续」；③自动续写须有硬止损（见角色意见·产品），触及止损时停下并说明；④界面显示**本轮**的 input / output token，而不只是 REQ-F-037 的会话累计值；⑤触及 ① 的阈值或 ③ 的止损时向用户给出预警。
> 与既有条文的关系：REQ-F-037「token 用量可见」已实现（会话累计值，`SearchSettings.tsx:114-119`），本条是对它的**增补**而非替代。REQ-NF-007 ①④ 属实现未达条文，按缺陷修复处理，**不新增条文**。

### 意见详述

**产品**｜「续写至写完」缺一个硬止损，这是本 CR 唯一会造成新损害的地方，已补成 REQ-NF-060 ③。裁定的本意是「别让答案被砍一半」，但字面执行意味着**只要模型不自然结束就一直续**——模型陷入重复或自我追加时，这就是一张没有上限的账单，而且是系统自动刷的，用户连按停的机会都没有（现在至少还要他说一句「继续」）。建议止损取两者先到：累计续写次数，或本轮累计 output token。具体数值交 P2。这不是推翻裁定，是把裁定放进一个封闭区间里。

**架构**｜占位摘要**不需要额外的模型调用**。`ToolResult` 里已经有 `summary` 字段（`registry.ts`：「Short line for the step row in the UI」，REQ-F-035 ① 用它渲染步骤行），每个工具执行时本就生成了它。把它当作占位摘要即可——零额外 token、零额外请求、零新增失败点。这一条很关键：如果摘要靠另起一次模型调用生成，我们就会在「已经超预算」的时刻再发一次请求，既贵又有顺序上的死结。建议 DEC 里把「摘要来源 = 既有 `summary`」写死，别留给实现期发挥。

**模块开发**｜可实现性通过。两处提醒：①`applyRetentionWindow` 的签名变更有**三个调用点**（`budget.ts:402` 的 `attempt(TOOL_RESULT_RETENTION_TURNS, null)`，以及 `425`、`426` 的降级档），降级档本身也要随之调整，否则会出现「先按预算裁过、再按旧降级档裁一次」的重复收紧。②轮内阈值检查要放在**发起工具调用前**而不是收到结果后——放在后面等于钱已经花掉了。这两点看似细节，但正是它们决定这个 CR 是真修好还是只是看起来修好。

**测试**｜⑤ **不是回归测试，是一次性证据**。它依赖真实 Provider、真实网络和真实网页内容，跑两次结果不会一样，不能进 `verify:all`。回归靠 ①–④ 的构造式单测。请不要把这条对照写进必选测试清单，否则它会在别人机器上随机变红。另：② 的断言要小心——「占位含要点」很容易写成「占位非空」这种过宽的断言，那等于没测。建议断言占位文本等于该次调用的 `summary` 原值，这是可精确比对的。
