## 问题陈述

为了验 `CR-20260912-turn-budget-continue` CP-3（输出截断后自动续写），我让模型连续写一份长讲义。结果：

```
正文字数: 13499
[60s] error: Provider stream timed out.
```

**13,499 个字正在往外流，第 60 秒整条被掐断。**

原因是 `AbortSignal.timeout(60_000)` 量的是**整条流的总时长**——它从创建那一刻起倒计时，不管有没有数据在来。于是「一直在产出的流」和「一个字都不出的流」被同一把尺子量。

而这个产品做的恰恰是长回答：深研究、长报告、被截断后自动续写。**它们天生活不过一分钟。**

早上那次 DeepSeek「60.2 秒零字节」也是同一把表报的，那次它报对了；这次它报错了。同一个数字盖住了两种完全不同的事。

## 实测（2026-09-14，用户自己那台服务器）

同一条提问，改前改后各跑一次：

| | 改前 | 改后 |
|---|---|---|
| 结局 | 第 60 秒 `Provider stream timed out` | 第 127 秒正常 `done` |
| 正文 | 13,499 字（被截断，丢失） | **29,340 字** |
| 模型调用 | 1 次（未完成） | **3 次**：输出 8,192 → 16,384 → 17,841 |

改后那三次调用顺带把另一条也验掉了：前两次都正好顶满 DeepSeek 的 8,192 输出上限，**触发了两次自动续写，全程无人输入「继续」**——`CR-20260912-turn-budget-continue` CP-3 的真实入口就此完成。

**一个被总时长挡住的功能，在墙拆掉之后才第一次跑起来。**
