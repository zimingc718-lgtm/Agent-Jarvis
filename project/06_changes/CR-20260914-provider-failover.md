## 问题陈述

2026-09-14 实测：DeepSeek（优先级 0）上游返回 200 之后**60 秒零字节**，而同一句话指定 OpenAI **3.6 秒答完**。

而当时这一轮只会超时——**链上排着一个能答的 Provider，系统却不会去试它**。`resolveActiveProvider` 只回队首，「队首不行就换下一个」这件事在上层根本无从做起。

同一天还有第二个场面：两个 Provider 的工具探测都曾被一次失败永久记成 `no`（已由 DEC-260 修掉）。即便判定正确，队首若真的不支持工具，此前的处置也是**整轮降级为纯对话**，而不是交给链上支持工具的那个。

## 三条边界，以及为什么是这三条

| 边界 | 为什么 |
|---|---|
| 只有**第一次**模型调用下沉 | 第二步及以后已经跑过工具，换模型等于重复副作用 |
| 只有**零可见输出**时下沉 | 已经吐字再换，用户会看到半句话被另一个模型接着写 |
| 每轮**最多一次** | 否则一条坏链能把一次提问变成 N 份账单 |

`usage` 不算可见输出——它在第一个字之前就到。2026-09-14 那次超时的实测事件序列正是 `start → usage → error`，整整 60 秒没有一个 `delta`。

## 角色意见

标准档只取与本 CR 直接相关的角色意见。

| 角色 | 意见 |
|---|---|
| 产品 | 换模型这件事**必须让用户看见**。一份不知道出自谁的答案，用户拿去做判断的时候不会想起来问。所以两句话都进对话记录区，而不是只写日志。 |
| 架构 | 边界写在包装生成器里，不写在调用方。调用方是 `runToolLoop` 的每一步，指望它记得「这是第几次调用、吐过字没有」就是把不变量交给记性。 |
| 模块开发 | 失败下沉换 Provider 时用**对方自己的默认模型**——把队首的模型名递给另一家，多半直接 400。 |
| 测试 | 断言的观察点是**打到了哪个 baseUrl**，不是传了哪个 model 字符串：首次调用本就传 `undefined`（用该 Provider 的默认模型），model 说明不了打给了谁。第一版断言就错在这儿，四条全红，产品代码其实是对的。 |
