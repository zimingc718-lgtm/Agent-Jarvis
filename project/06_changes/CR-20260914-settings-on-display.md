## 问题陈述

两件事，同一个根：**屏幕上那块地方谁说了算。**

1. 设置全在弹窗里。要换 Provider 就得盖住正在看的报告，改完关掉才能看见效果——而这些面板恰恰是要对着屏幕上的东西改的。
2. 控制台 `fixed bottom-0` 浮在展示屏上，用户手动展开对话时报告被盖约 78%。2026-09-12 只做了纵向缓解（面板高度上限 75vh → 58vh），报告**顶部**始终可读，中下部照旧被盖——这条当时就如实登记为「仅追认为过渡」，用户 2026-09-13 又提了一次。

另有一件此前没人看得见的事：**工具按可用性动态注册**（REQ-NF-008 ④），没技能就没有技能工具，联网关掉就没有 `web_search`。这件事此前只有模型知道，用户既看不到系统一共有哪些能力，也看不到某一个这轮为什么不在。

## 角色意见

标准档只取与本 CR 直接相关的角色意见。

| 角色 | 意见 |
|---|---|
| 产品 | 设置搬上屏之后，☰ 抽屉里的入口**不删**：两个入口对应两种习惯，删掉一个是替用户做决定。工具面板的价值在于「未注册的也列出来」——看不见的能力等于不存在，这是本轮几个缺陷的共同形状。 |
| 架构 | 让出高度而不是分栏：控制台的形状、REQ-F-090 的列宽与居中一个都不动，改的只是展示屏可用区的下边界。用 `ResizeObserver` 取实测值，因为那个高度有四五种状态。 |
| 模块开发 | `/api/tools` 必须调 `buildRegistry` 与同一份 `ToolContext`，不另写近似判定——两份判定迟早分岔，分岔那天用户看到的就是一份假名单。 |
| 测试 | TEST-330 ⑥ 断言 `web_search` **落在「未注册」那一组里**，而不只是「出现在页面上」：一个把未注册项混在一起显示的实现照样能通过后者。CP-4 的观感要真实入口，单测只能断言那个 CSS 变量被用上了。 |
