## 流程偏差记录（如实登记）

**CP-3 执行时发生了一次数据事故，如实记录如下。**

CP-1 把 `deleteKnowledge` 从硬 `rm` 改成归档实现，这次代码修改完成后，我没有重新构建并重启生产服务器就直接运行了 CP-3 的迁移脚本（`--commit` 模式，对用户真实的 `.data/knowledge/` 执行）。当时运行中的服务器由 `npm run serve:local` 起，使用的 `.next-prod` 构建产物时间戳是 2026-09-16 22:45——早于当天（2026-09-17）对 `deleteKnowledge` 的代码修改，因此服务器实际执行的仍是**旧版本**的 `deleteKnowledge`（纯 `rm`，无归档）。

后果：迁移脚本报告"已归档 246 条，失败 0 条"，但这 246 条实际是被**硬删**的——`.data/knowledge/archive/` 目录在事后核对时是空的（只有脚本自己写的两份清单 JSON），`.data/knowledge/` 根目录条目数从 253 降到 7，246 条真实笔记内容不在本机任何可恢复的位置。

发现与处理：
1. 执行后核对归档目录为空，立即停止后续操作，未再进行任何写入类动作。
2. 检查确认根因：构建产物时间戳早于代码修改时间戳（`CLAUDE.md` 本就有"改完代码要重建并重启服务"的明文规则，这次没有遵守）。
3. 排查本机可能的恢复途径：Windows 回收站（直接核对，246 个文件名均不在其中——Node 的 `rm()` 不经过回收站）、卷影副本（`vssadmin list shadows` 无管理员权限被拒，未能核实，已告知用户可自行用提升权限的终端或资源管理器"以前的版本"尝试）、OneDrive 云端回收站/版本历史（本项目目录在 OneDrive 同步范围内，是本机之外最可能保留副本的地方，但需要用户自己登录 onedrive.com 核对，我这边没有访问其账户网页版的手段）。
4. 清理干净构建缓存后重新执行 `npm run build:local`，停掉旧的服务进程（确认端口 3000 只有它在监听，未触碰其它不相关进程），等 `serve:local` 的看护自动拉起新进程，用一条一次性测试条目走"存入 → 删除 → 确认落在 `archive/`"验证归档确实生效。
5. 把 246 条被删条目的完整清单（name/title/source/entity/docType）留在 `.data/knowledge/archive/_migration-2026-09-17T17-24-43-388Z.json`——即使内容无法恢复，至少有一份可核查的"丢了什么"的清单，供用户判断是否需要重新收集。
6. 向用户完整披露了上述 1-5 点，并在获得用户"现在执行"的明确指令后才继续推进本 CR 剩余工作——该指令是在已知悉事故全貌的前提下给出的。

**这不是"归档设计有问题"，是"没有确认部署的代码是当前代码就对生产数据执行了写操作"**。归档设计本身经事后验证是正确的（见第 4 点）。记录在此，供以后任何"要对生产数据做一次性操作"的场景强制先做同一件事：确认服务的构建产物时间戳晚于相关代码的最后一次修改时间戳，而不是只看服务"健康检查"式的 200 响应——一个跑着旧代码的服务器对只读路由同样会稳定返回 200。
