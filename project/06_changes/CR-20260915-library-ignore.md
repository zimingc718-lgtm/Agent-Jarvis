## 问题经过

CR-20260915-board-tick-burst 合并后收口，按惯例补一次快照。快照写成了，然后 `verify`：

```
FAIL UNBASELINED_FILE 资料库/AIDC-供电架构与电网/README.md
FAIL UNBASELINED_FILE 资料库/AIDC-供电架构与电网/清单.md
```

看现场：仓库根下 `资料库/` 建于 11:44:13，`snapshot` 跑在 11:45:21，把它的 **256 个文件（253 MB）**全数写进了 `baseline.json`（该文件从 38 KB 涨到 82 KB）；而 11:46:10 又多出两个 `.md`——目录还在被续写（这棵工作树在 OneDrive 下，内容正一边同步一边落地；应用的归档功能同样往这类目录里写）。

三点值得记下：

1. **这不是快照的错，也不是用户的错。** `discover_controlled_files` 按文件系统遍历，忽略表里没有它，于是用户的数据目录被当成了产品源码。谁在这棵树里放数据目录都一样。
2. **失败形态是「慢性红」**：基线一旦纳管一个活的目录，`verify` 会在每次同步、每次归档之后变红，而红的原因与产品无关。门禁长期为噪声变红，比不变红更危险——人会开始无视它。
3. **那次污染的快照没有提交。** 发现后立刻 `git restore` 回到 `seq=108`（CR-20260915-board-tick-burst 的合并前快照），链上没有留下污染记录；本 CR 合并后再补的那次快照才是收口快照。
4. **资料库该不该进版本库，是另一个问题。** 本 CR 初稿顺手在 `.gitignore` 也加了一条，用户当天即裁定相反（INPUT-2026-09-15-028），该条已撤回。受控基线侧的忽略不受影响——两件事本就该分开判。
