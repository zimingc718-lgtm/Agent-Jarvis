## 问题经过

用户在 INPUT-2026-09-18-001 第 9b 条提出："做个学术会议参会前瞻的洞察，也支持放在动态屏展示，包括日程，panel，核心专家等，也支持对话调整。"INPUT-2026-09-18-002 进一步确认"参考业界最佳实践"这句话是专门针对本条（与第 8 条）的内容质量要求，不是对整批需求的通用提醒。

投入实现前的代码核对发现：

1. `src/lib/tools/display-tools.ts` 的 `save_insight`/`show_insight` 是完全通用的机制——`save_insight` 接受任意 HTML 片段（"把 HTML 报告保存为洞察并显示在展示屏上"），不对内容主题做任何限制或过滤（`tests/tool-suites.test.ts` ⑧ 已如实记录这条既有风险接受："save_insight 不对 HTML 来源做任何过滤"）；`mode: replace` 与带 `insightId` 的追加已经是"对话调整"这句话要的能力——一份已存在的洞察可以被后续对话追加或整篇重写。
2. `src/lib/display-document.ts`（展示层的排版样式）同样是主题无关的通用 HTML 排版（标题、段落、列表），没有为任何特定报告类型做特殊处理。
3. 本仓库的技能机制严格要求用户手动上传（拖放或点选，见 `CR-20260910-skill-intake`、`CR-20260915-unified-upload-entry`），不存在"随代码库预置技能"的路径——因此"写一个会议前瞻技能"不是这个 CR 能交付的代码变化点，那是用户自己以后想用就自己传的事，不受本 CR 约束也不该被本 CR 悄悄决定。
4. 既有测试（`tests/tool-suites.test.ts`、`tests/tool-suites-append.test.ts`、`tests/skill-report-bridge.test.ts`）已经用通用 HTML 内容覆盖了 `save_insight`/`show_insight` 的全部代码路径；"会议前瞻"这类主题不会走到任何这些测试没有覆盖的新代码分支。

结论：**这条需求所需要的机制已经完全存在**，不产生任何代码变化点。剩下唯一没有答案的问题是"模型被这样问的时候，会不会自己想到这样做、产出的内容结构像不像一份及格的参会前瞻"——这是模型行为层面的问题，机器检查回答不了，只能靠真实入口核验（见 `scripts/probe-conference-preview-insight.mjs`）。
