# 客户技术准入解读

客户这一类对象只看三样：**容量、商业白皮书、技术准入要求**。**不涉及项目交付**——
交付进度、验收、售后都不在这里，那是另一个系统的事，混进来会让看板变成项目管理工具。

这本技能解决的是同一个问题：**一份几十页的文件里，哪几句话是真正的门槛。**

## 1. 硬要求 vs 软偏好

只有硬要求值得抽成字段。分辨靠措辞：

| 硬要求 | 软偏好 |
|---|---|
| 必须、应、需、shall、must、required | 宜、建议、推荐、should、preferred、nice to have |
| 带数值门槛与单位 | 只有形容词（高可靠、良好的兼容性） |
| 指明具体标准号或认证 | 泛指「符合相关国家标准」 |
| 写在「准入条件 / 技术要求」章节 | 写在「愿景 / 合作展望」章节 |

**判据**：这一条不满足，我们会不会被直接排除？会 → 硬要求。

软偏好不要丢掉，但它们属于知识条目里的正文，不要变成看板上的字段。

## 2. 抽什么

对客户对象，有意义的字段是：

- `capacity`：这个客户的规模口径（装机容量、年采购量、站点数）。**照抄他们自己的
  口径与单位**，不要换算。1.2 GW 和 1200 MW 在他们文件里是两种写法，引文要能对上。
- `nextLabel` / `nextDate`：下一个与我们有关的时间点（供应商名录申报截止、
  技术交流窗口、招标预告日期）。
- `summary`：一句话说清这个客户是做什么的、我们与他们的关系处在哪一步。
- `change`：本次材料带来的变化。

## 3. 白皮书怎么切条目

一份白皮书通常混着三种内容：公司介绍、技术路线主张、准入要求。**按这三块切条目**，
不要整本存成一条：

- 准入要求那一章是最常被检索的，单独成条，`doc_type` 写「技术准入要求」。
- 技术路线主张单独成条，`doc_type` 写「白皮书」。
- 公司介绍通常没有检索价值，可以不入库。

标题带上客户名、文件名与版本年份，例如
`客户 C 储能系统技术规范 2026 版 第 5 章 准入要求`。

## 4. 常见的读错

- **把「推荐配置」当成「最低要求」**。前者是他们希望的，后者是必须的，差价很大。
- **把某一个项目的特殊要求当成通用准入**。看清文件抬头是通用规范还是某标段的附件。
- **把旧版本的门槛当现行**。文件上的年份和「代替 XX 版」那一行要一起读。
- **把单位读串**：kW / kWh、MW / MWh、V / kV。抽字段时把单位连同数字一起放进引文里，
  机器会核对值是否出现在引文中，但**单位读错它看不出来**。

## 5. 写入流程

1. 先 `ingest_url` 或 `save_knowledge` 把材料存成条目（留原链接）。
2. 再 `extract_fields`，每个字段配一句**逐字引文**，遵守 [证据规范]。
3. 客户材料常常来自邮件附件或非官网域名——那就会进**待采纳区**，这是正常的，照实说。

## 6. 汇报

按「我们能不能进」组织，而不是按文件结构：

1. 硬门槛有哪几条，我们目前满足哪几条。
2. 明确不满足的，缺口是什么（数值差多少、缺哪个认证）。
3. 有截止日期的动作。
4. 读不准的地方——**说出来**，不要替用户决定。
