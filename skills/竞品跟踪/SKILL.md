# 竞品跟踪

目标不是「知道友商发生了什么」，是**知道有哪几件事需要我们反应**。前者是订阅新闻，
后者才是竞品跟踪。库里每天多十条无关变化，真正要紧的那条就被埋了。

## 1. 配哪些源

按可读性和信噪比排，**先配前两类，够用了再往下加**：

| 优先 | 页面 | 为什么 |
|---|---|---|
| 1 | 产品页 / 规格页 | 参数变化是最硬的信号，且改动少、改必有因 |
| 1 | 发布说明 / 固件更新记录 | 时间戳清楚，一条一条本来就是结构化的 |
| 2 | 新闻 / 公告列表页 | 有噪声，但重大动作一定在这儿 |
| 3 | 博客、案例页 | 多为营销文，信噪比低 |
| 不配 | 首页、社交媒体、聚合新闻站 | 首页天天动但几乎不含事实；聚合站是二手的 |

**不要配需要登录或脚本渲染的页面**：采集会稳定地报「解析失败」，而解析失败会一直亮
在卡片上，把真正的异常淹掉。遇到这种页面，告诉用户这个源取不到正文，请人工看。

一个对象配 2–4 个源就够。配到十个，你看的是噪声。

## 2. 一条变化值不值得记

采集本身会机械地给出「新增 N 行，首条是……」。**要不要把它升级成一条变更、进而让
卡片变未读，由你判断。**

值得记：

- 参数变了：功率、容量、效率、接口、认证型号。
- 价格或商务条款变了。
- 新产品、新型号、停产。
- 认证 / 准入状态变了（拿到某个并网认证、进入某个名录）。
- 明确的时间点：发布日期、交付窗口、截止日。

不值得记：

- 版式、导航、页脚、备案号、图片替换。
- 措辞润色而事实没变。
- 一条新闻只是转述了他们之前已经公布过的事。
- 新增了一个联系方式或招聘启事。

**判据**：这条变化会不会改变我们的某个决定？不会就不要记——记了就等于在用户的注意力
上花了一笔钱。

## 3. 变更摘要怎么写

一行，说清**变了什么**，不要说「有更新」。

- 好：`X-3000 额定功率由 250kW 提高到 300kW（规格页）`
- 好：`新增欧洲并网认证 VDE-AR-N 4110，公告日期 2026-09-08`
- 坏：`产品页有更新`、`发布了新内容`、`可能有重要变化`

要求：

1. 用**变化前 → 变化后**的形式，只有一侧时说清是新增还是移除。
2. 数字照抄原文，带单位。
3. 不写你的推测。「疑似为应对我们的降价」这类判断放在对话里说，不要写进字段。

## 4. 从变化到字段

若这次变化里有该对象的字段值（容量、下一里程碑等），流程是：

1. `ingest_url` 把那个页面抓成知识条目（留下原链接）。
2. `extract_fields` 带**逐字引文**把值写到对象上，遵守 [证据规范]。

不要跳过第 1 步直接写字段：没有本地条目，引文就无处核对，写进去的值等于没有来源。

## 5. 汇报给用户时

说三件事，按这个顺序：

1. **哪几个对象有真变化**，每个一行摘要。
2. **哪几个对象采集异常**（失败 / 解析失败 / 从没配源）——这是「我们没在看」，
   不是「他们没动静」。
3. 需要用户决定的事：要不要采纳某条提议、要不要加一个源。

没有变化时就说没有变化。**不要为了让汇报看起来有内容而把版式改动说成动向。**
